<details>
<summary>📝 Текстовая версия шпаргалки</summary>

Ментальная модель Git: рабочая область → `git add` → индекс → `git commit` → история. Коммит = контрольная точка.

- Минимальный цикл: `git init` → `git add .` → `git commit -m 'init'` → `git remote add origin ...` → `git push -u origin main`.
- Два маршрута: соло (main → push без веток и PR) и команда (ветка + PR; защищённый main — только через PR).
- Git — локальный инструмент, GitHub — облачный хостинг. Не путать.
- Промпт для OpenCode одной фразой: «проверь status + diff, сгенерируй commit message, выполни add -A && commit && push; стой, если увидишь .env/ключи».

| Ошибка | Решение |
|---|---|
| «Please tell me who you are» | Настроить user.name / user.email |
| Push требует пароль | PAT или SSH |
| origin уже существует | `git remote set-url` |
| Путаница main/master | `git branch -M main` |

</details>

## Основная идея

Git выполняет три основные задачи:

1. **Записывает снимки**: сохраняет «текущее состояние кода» под именем (commit)
2. **Сравнивает изменения**: позволяет в любой момент увидеть, «что изменилось»
3. **Синхронизирует работу**: отправляет ваши commit на удалённый сервер (GitHub) или загружает чужие commit

Самая важная ментальная модель показана на схеме:

```text
Рабочая папка (Working Tree)
  |  git add
  v
Индекс (Index)
  |  git commit
  v
История (Commits)
```

::: info Что означают эти три термина?

- **Рабочая область**: папка, которую вы редактируете (видимые вам файлы)
- **Индекс**: набор изменений, «выбранных для коммита» (ещё не вошедших в историю)
- **Коммит (commit)**: «точка сохранения», к которой можно вернуться; каждый коммит должен объяснять, «что и зачем я сделал»

:::

::: details В чём разница между Git и GitHub?

- **Git**: инструмент контроля версий, работающий на вашем компьютере.
- **GitHub**: сайт для хостинга Git-репозиториев. На него можно отправить локальный репозиторий и работать вместе с другими.

:::

Далее вы пройдёте «минимальный рабочий цикл»: инициализация репозитория → первый коммит → отправка на GitHub.

Затем вы изучите два сценария:

| Ваша ситуация | Рекомендуемый подход | Ключевые слова |
|---|---|---|
| Вы пишете один (личный проект / небольшая утилита) | Коммиты и push прямо в `main` (ветка и PR не обязательны) | `status → diff → commit → push` |
| Вы работаете вместе (несколько человек / CI / проверка кода) | Ветка + PR | `branch → PR → merge → pull` |

::: tip Роль OpenCode
Вам не нужно заучивать множество команд Git. Практичнее:

1) попросить OpenCode сначала показать сводку изменений (на основе `git status` / `git diff`);
2) затем попросить его создать сообщение коммита и выполнить `add/commit/push`.
:::

## Повторите за мной

В поле TUI OpenCode добавьте `!` перед командой (например, `!git status`). Если вам привычнее обычный терминал, это тоже подходит.

### Шаг 1: настройте данные автора Git (один раз)

**Зачем**
В историю коммитов записываются данные автора; без них первый commit может завершиться ошибкой.

```bash
git config --global user.name "твоё имя"
git config --global user.email "твоя почта"

# Проверяем
git config --global --get user.name
git config --global --get user.email
```

**Вы должны увидеть**: последние две строки выведут заданные имя и адрес электронной почты.

::: warning Для рабочих проектов
На рабочем компьютере лучше использовать рабочий адрес; для личного проекта — привычный личный адрес.
:::

### Шаг 2: создайте репозиторий (init или clone)

**Зачем**
Без репозитория (каталога `.git`) Git некуда записывать «историю».

::: code-group

```bash [Есть локальная папка (новичку сюда)]
# Переходим в каталог проекта
cd /path/to/your/project

# Инициализируем репозиторий
git init
```

```bash [Клонирую готовый репозиторий с GitHub]
git clone https://github.com/<owner>/<repo>.git
cd <repo>
```

:::

**Вы должны увидеть**: `git init` сообщит об инициализации репозитория, а `git clone` загрузит код локально.

Заодно добавьте `.gitignore` (чтобы не отправить в репозиторий артефакты сборки, кэш и ключи):

```bash
# Зависимости и артефакты сборки
node_modules/
dist/
build/

# Логи
*.log

# Локальные переменные окружения (не коммитить в репозиторий)
.env
.env.local

# Системное/мусор редакторов
.DS_Store
.idea/
```

::: tip Не хотите писать его вручную? Попросите OpenCode выбрать «файлы для игнорирования»

Достаточно одной фразы: OpenCode создаст или обновит `.gitignore` на основе содержимого проекта и `git status`:

```text
Проверь, какие файлы не нужно коммитить, и добавь в .gitignore.

Требования:
1) Сначала запусти и посмотри git status / git diff (только смотри, не коммить/не пушь)
2) Меняй/создавай только .gitignore, потом покажи его содержимое и объясни каждый пункт
3) Если найдёшь .env, ключи, токены и подобные секреты — остановись и предупреди меня
```

:::

::: warning У `.gitignore` есть «ловушка для новичков»
`.gitignore` действует только для «файлов, которые Git ещё не отслеживает».

Если файл уже был закоммичен, добавление его в `.gitignore` не удалит его. Сначала правильно убрать его из отслеживания репозитория (сохранив локальный файл), а затем создать коммит:

```bash
git rm --cached <file>
git commit -m "chore: stop tracking <file>"
```

Если это ключ или пароль, недостаточно выполнить `rm --cached`: немедленно отзовите ключ на соответствующей платформе и создайте новый.
:::

::: warning Если у проекта уже есть собственный .gitignore
Оставьте существующее содержимое и не заменяйте его принудительно этим примером.
:::

### Шаг 3: создайте первый коммит (first commit)

**Зачем**
Первый коммит — это «точка сохранения 0». С этого момента к этому состоянию можно вернуться в любой момент.

```bash
# Смотрим текущее состояние
git status

# Добавляем изменения в индекс (в первый раз обычно всё сразу)
git add .

# Коммитим
git commit -m "init"
```

**Вы должны увидеть**: `git status` сменит множество красных «неотслеживаемых/изменённых» файлов на «working tree clean» (чистое рабочее дерево).

Посмотрите историю коммитов:

```bash
git log --oneline -5
```

**Вы должны увидеть** строку `init` с коротким хешем перед ней.

### Шаг 4: отправьте локальный репозиторий на GitHub (первая синхронизация)

**Зачем**
История Git хранится на вашем компьютере; после отправки на GitHub у вас появятся «удалённая резервная копия и точка для совместной работы».

1) Создайте на GitHub пустой репозиторий (рекомендуется не добавлять README / .gitignore, чтобы репозиторий оставался пустым).

2) Проверьте, в какой ветке вы сейчас находитесь:

```bash
git branch --show-current
```

Если вы видите `master`, рекомендуется переименовать её в `main` (команду можно выполнить в текущей ветке):

```bash
git branch -M main
```

3) Привяжите удалённый репозиторий и отправьте `main`:

```bash
git remote -v

# Если репозиторий создан через git init: добавляем origin
# Если склонирован через git clone: origin обычно уже есть, пропускаем
git remote add origin https://github.com/<owner>/<repo>.git

# Пушим обязательно в main
git checkout main
git push -u origin main
```

**Вы должны увидеть**: на странице репозитория GitHub появилась ветка `main`.

::: warning Если push запрашивает пароль
GitHub больше не поддерживает отправку по паролю аккаунта. Вам нужно:

- использовать HTTPS: при запросе учётных данных указать **Personal Access Token** (PAT);
- или использовать SSH: добавить SSH-ключ в GitHub.

Это настройка аккаунта GitHub, не связанная с OpenCode; если возникнут проблемы, следуйте подсказкам GitHub.
:::

### Шаг 5: повседневный цикл разработки в одиночку (без веток и PR)

**Зачем**
В личном проекте «ветка + PR» необязательны. Надёжный ритм такой: после каждой небольшой функции создавайте точку сохранения (commit), к которой можно вернуться, и отправляйте её на GitHub.

Достаточно научиться давать OpenCode короткую команду:

```text
Подведи итог изменений, закоммить и запушь.
```

::: details Хотите надёжнее (рекомендуется)

Если не хотите отправлять изменения «вслепую», используйте эту фразу (она тоже короткая, но безопаснее):

```text
Сначала проверь git status + git diff, подведи итог и предложи commit message;
После моего подтверждения коммить и пушь.

Внимание: если найдёшь .env, ключи, токены и подобные файлы — остановись и предупреди меня.
```

::: 

Если вы предпочитаете всё проверить самостоятельно, выполните основные команды через `!`:

```bash
git status
git diff
```

**Вы должны увидеть**:

- OpenCode сначала обобщит изменения, затем предложит сообщение коммита;
- после успешной отправки в репозитории GitHub будет виден последний коммит.

::: warning Опасно ли просить его выполнить push одной фразой?
Да, поэтому используйте схему: сначала `status/diff`, затем commit/push. Так у вас всегда остаётся возможность последней ручной проверки.
:::

::: details Сценарий совместной работы (необязательно): ветка + PR

Этот сценарий обычно нужен, если:

- в репозитории включена защита ветки `main` (прямой push запрещён);
- перед каждым объединением нужно запускать CI и проверку кода.

```bash
# Создаём ветку и коммитим
git checkout -b feature/first-change
git add -A
git commit -m "feat: first change"
git push -u origin feature/first-change
```

Затем создайте PR на GitHub: в base выберите `main`, а в compare — `feature/first-change`.

После объединения синхронизируйте локальный репозиторий:

```bash
git checkout main
git pull
```

:::

### Шаг 6: поддерживайте синхронизацию с GitHub

**Зачем**
Если код изменился на GitHub (вы сделали push с другого компьютера, объединили PR или изменения отправил кто-то другой), локальную копию нужно обновить.

Рекомендуемая привычка:

- в начале работы — `pull`;
- в конце — `commit + push`.

```bash
git checkout main
git pull
```

Необязательно: удаление локальной ветки:

```bash
git branch -d feature/first-change
```

**Вы должны увидеть**: в `git log --oneline -5` появился коммит, недавно объединённый через PR.

::: info Что делает `/undo` (не путайте)

- `/undo` отменяет «изменения файлов, вызванные последним сообщением».
- Это не `git reset`: команда не отменяет историю, которая уже была закоммичена (commit) или отправлена (push).

Если вы уже выполнили `git commit`, исправьте проблему новым commit; если уже сделали `git push`, не переписывайте историю без необходимости.

:::

## Типичные проблемы

| Симптом | Причина | Решение |
|-----|-----|-----|
| Симптом | Причина | Решение |
| `git commit` сообщает «Please tell me who you are» | Не настроены данные автора | Настройте `user.name` / `user.email` по шагу 1 |
| `git status` показывает множество файлов, и вы боитесь коммитить | Непонятно, какие файлы должны попасть в репозиторий | Сначала создайте `.gitignore`, затем проверьте через `git status` |
| `git push` запрашивает пароль и завершается ошибкой | GitHub запретил отправку по паролю аккаунта | Используйте PAT (HTTPS) или SSH-ключ |
| Неверная ветка по умолчанию на сервере (путаница main/master) | Имена веток не совпадают | Сначала проверьте `git branch --show-current`, что вы в `master`, затем выполните `git branch -M main` и отправьте `main` |
| `.env` случайно попал в коммит | `.gitignore` не настроен или файл уже был закоммичен | Немедленно удалите файл и создайте ключ заново; затем обработайте историю репозитория (не откладывайте) |
| `git remote add origin` сообщает, что адрес уже существует | Репозиторий клонирован с GitHub | Пропустите добавление; для смены адреса используйте `git remote set-url origin <url>` |
| Вы отметили README на GitHub, и push сообщил о конфликте | Удалённый репозиторий не пуст | Проще всего создать новый пустой репозиторий или выполнить `git pull --rebase`, а затем push |
| Прямой push в main отклонён | В репозитории включена защита ветки | Используйте сценарий «ветка + PR» или измените правила репозитория |
