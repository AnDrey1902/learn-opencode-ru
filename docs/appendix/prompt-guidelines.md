# Нормы инженерии промптов

> Документ задаёт нормы написания промптов в учебнике OpenCode: все шаблоны держат единый высокий стандарт качества.

---

## 🎯 Главные принципы

### 1. Структура прежде всего (Structure First)

Каждый шаблон обязан иметь явную структуру уровней:

<!-- @click-to-copy -->
```
Определение роли → описание задачи → спецификация входа → спецификация выхода → примеры → ограничения
```

### 2. Обязательные few-shot (Example-Driven)

Сложные задачи обязаны давать 1–2 конкретных примера, чтобы модель понимала ожидаемые форматы входа и выхода.

### 3. Явная цепочка мыслей (Chain of Thought)

Для рассуждающих задач явно ведите пошаговое мышление «сначала разбор, потом вывод».

### 4. Количественные критерии оценки (Quantified Criteria)

Любые оценки и шкалы обязаны иметь явные критерии и определения каждого диапазона баллов.

### 5. Механизм обработки ошибок (Graceful Degradation)

Шаблон включает: как действовать при неполном входе, как уточнять при двусмысленности, как отвечать вне зоны возможностей.

### 6. Механизм самопроверки (Self-Verification)

Перед выводом сложных задач — самопроверка на соответствие требованиям.

### 7. Консистентность плейсхолдеров (Consistent Placeholders)

Единый синтаксис плейсхолдеров на весь документ, ясное разделение обязательных и необязательных.

---

## 📋 Стандартная структура шаблона

<!-- @click-to-copy -->
```markdown
## Роль
Вы — [профессиональная роль], мастер [главная способность]. [Дополнительное якорение роли]

## Задача
[Ясно опишите задачу для выполнения]

## Входные данные
### Обязательные
- Имя переменной:【описание переменной】

### Необязательные
- Имя переменной:【описание переменной?】(по умолчанию:xxx)

## Формат вывода
Выводите по структуре:
1. [Пункт вывода 1]
2. [Пункт вывода 2]
...

## Примеры

### Вход
[Конкретный пример входа]

### Вывод
[Соответствующий идеальный вывод]

## Ограничения
- ✅ Надо:[позитивное поведение]
- ❌ Нельзя:[негативное поведение]

## Чек-лист самопроверки
Перед завершением убедитесь:
- [ ] [Пункт проверки 1]
- [ ] [Пункт проверки 2]

## Обработка ошибок
- Не хватает главной информации — сначала спросите пользователя
- Задача вне зоны возможностей — объясните причину и предложите альтернативу
```

## 🏷️ Нормы плейсхолдеров
<AdInArticle />

### Синтаксис

| Тип | Синтаксис | Пример |
|------|------|------|
| **Обязательная переменная** | `【имя переменной】` | `【язык программирования】` |
| **Необязательная переменная** | `【имя переменной?】` | `【фреймворк?】` |
| **Со значением по умолчанию** | `【имя переменной=значение】` | `【стиль=лёгкий】` |
| **Выбор одного** | `【вариант1/вариант2/вариант3】` | `【фэнтези/город/романтика】` |
| **Блок текста** | `[описание вставки]` | `[вставьте код]` |

### Сравнение примеров

**❌ Плохое написание**:
```
Тип:фэнтези/город/романтика
Язык:язык
Вставьте код
```

**✅ Хорошее написание**:
```
Тип:【фэнтези/город/романтика/детектив/фантастика】
Язык:【язык программирования】

[вставьте код]
```

## 📊 Нормы шкал оценок

В шаблонах со шкалами обязаны определяться критерии:

### Пример: оценка качества кода

| Балл | Читаемость | Производительность | Безопасность | Покрытие тестами |
|------|--------|------|--------|---------|
| 9-10 | Имена ясные, комментарии полные | O(n) и лучше | Без уязвимостей | >90% |
| 7-8 | Имена разумные, главные комментарии | O(n log n) | Низкие риски | 70-90% |
| 5-6 | В основном читаемо | O(n²) | Средние риски | 50-70% |
| <5 | Понять тяжело | O(n³)+ | Высокие риски | <50% |

**Расчёт сводного балла**: читаемость×0.3 + производительность×0.3 + безопасность×0.25 + покрытие тестами×0.15

---

## 👤 Нормы определения ролей

### Элементы

1. **Профессиональная роль**: кто вы
2. **Главная способность**: в чём сильны
3. **Аудитория**: кому служите (необязательно)
4. **Особенности стиля**: манера работы (необязательно)

### Пример

**❌ Плохое написание**:
```
Вы — помощник.
```

**✅ Хорошее написание**:
```
Вы — senior-инженер по технической документации: сложные вещи объясняете просто и понятно.
Новички хвалят ваши объяснения как «наконец-то понял».
```

## ⚖️ Нормы ограничений

Символами ✅ и ❌ чётко делите позитивное и негативное поведение:

```markdown
## Ограничения
- ✅ Проблемы — конкретно до строк
- ✅ К каждой проблеме — рекомендация
- ✅ Отмечайте сильные места
- ❌ Не подменяйте объективные критерии вкусовщиной
- ❌ Не критикуйте без предложений
```

## 🔧 Нормы обработки ошибок

Каждый шаблон включает раздел обработки ошибок:

<!-- @click-to-copy -->
```markdown
## Обработка ошибок
- Не хватает информации — перечислите недостающее и объясните, зачем нужно
- Проблема вне зоны возможностей — объясните и предложите каналы помощи
- Несколько независимых проблем — предложите разбирать по одной
```

## ✅ Нормы чек-листов самопроверки

Сложные задачи включают чек-лист самопроверки:

<!-- @click-to-copy -->
```markdown
## Чек-лист самопроверки
Перед завершением убедитесь:
- [ ] У каждого главного героя ясная арка
- [ ] Ритм завязки, развития и кульминации разумен
- [ ] Главный конфликт держит весь текст
- [ ] Изюминок хватает для целевой аудитории
```

## 🤖 Нормы description для Agent и Skill

### Шаблон структуры

<!-- @click-to-copy -->
```yaml
description: |
  [Одна фраза о главной способности]
  Даёт: [ресурсы навыка]
  Применимо: [сценарий срабатывания 1], [сценарий срабатывания 2]
  Неприменимо: [граничные сценарии 1], [граничные сценарии 2]
```

### Пример

**❌ Плохое написание**:
```yaml
description: Эксперт по ревью кода
```

**✅ Хорошее написание**:
```yaml
description: |
  Эксперт по ревью кода: уязвимости безопасности, проблемы производительности, качество кода.
  Сценарии: ревью PR, проверки здоровья кода, аудиты безопасности.
  Неприменимо: генерация кода, реализация функций, написание тестов.
```

---

## 📝 Чек-лист проверки

Перед публикацией шаблона убедитесь:

- [ ] Есть явное определение роли
- [ ] Входные данные делят обязательные и необязательные
- [ ] Есть полная спецификация вывода
- [ ] Сложные задачи с few-shot-примерами
- [ ] Шкалы с количественными критериями
- [ ] Есть ограничения (✅ и ❌)
- [ ] Есть механизм обработки ошибок
- [ ] Единый синтаксис плейсхолдеров
- [ ] Нет ошибок форматирования
