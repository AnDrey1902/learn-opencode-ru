## Основная идея

### Сценарии автоматизации документации

| Тип документа | Когда генерировать | Как помогает AI |
|---------|---------|-----------|
| README | Старт проекта / крупные обновления | Разобрать структуру проекта и создать |
| API-документация | Интерфейсы готовы | Извлечь из кода и создать |
| Сообщения Commit | Каждый коммит | Проанализировать изменения и создать |
| Описание PR | Подача PR | Свести коммиты и создать |

## Повторите за мной

### Шаг 1: создайте README

**Зачем**
Хороший README — лицо проекта.

Переключитесь на Build Agent:

```
@explore разбери структуру проекта и создай профессиональный README.md:

Включи разделы:
1. Название и описание проекта
2. Возможности (Feature list)
3. Быстрый старт (установка и запуск)
4. Примеры использования
5. Описание настроек
6. Руководство для контрибьюторов
7. Лицензия

Сохрани в README.md
```

### Шаг 2: создайте сообщение commit

**Зачем**
Нормальные сообщения коммитов легко отслеживать.

Сначала посмотрите изменения:

> В OpenCode TUI сообщение с `!` в начале выполняет shell-команду и подтягивает вывод в диалог: https://opencode.ai/docs/tui

```
!git diff
```

Затем попросите AI создать:

```
По изменениям выше создай сообщение commit по спецификации Conventional Commits:
- Формат: type(scope): description
- type: feat/fix/docs/style/refactor/test/chore
- Коротко и ясно, не длиннее 50 символов
```

Выполните коммит:

```
!git add . && git commit -m "feat(auth): add email verification on registration"
```

### Шаг 3: создайте описание PR

<AdInArticle />

**Зачем**
Понятное описание PR помогает ревьюеру разобраться.

> Получение списка свежих коммитов (пример):

```
!git log --oneline -10
```

```
По истории коммитов выше создай описание PR:

## Обзор изменений
(резюме одной фразой)

## Детали изменений
(главные правки по пунктам)

## Как тестировалось
(что проверялось)

## Связанные Issue
(номера связанных issue)
```

### Шаг 4: отмена через /undo

**Зачем**
Ошибочные правки AI можно откатить.

Если правки AI не нравятся:

```
/undo
```

**Вы должны увидеть**: сессия вернётся к предыдущему сообщению пользователя, а связанные файловые патчи после него откатятся (восстановлению файлов нужен Git-репозиторий). Подробнее: https://opencode.ai/docs/tui#undo или [Приложение/Шпаргалка команд](../appendix/commands).

Чтобы вернуть только что отменённые сессию и файлы:

```
/redo
```

> `"snapshot": false` отключает только восстановление файлов, но не undo/redo сессии. Исходники: [`session/revert.ts:38-98`](https://github.com/anomalyco/opencode/blob/v1.18.22/packages/opencode/src/session/revert.ts#L38-L98),[`config.ts:52-55`](https://github.com/anomalyco/opencode/blob/v1.18.22/packages/core/src/v1/config/config.ts#L52-L55).

### Шаг 5: допишите комментарии в коде

**Зачем**
Хорошие комментарии — живая документация.

```
@src/services/payment.ts добавь в этот файл JSDoc-комментарии:
- К каждой экспортируемой функции
- С описанием параметров и возвращаемого значения
- С примером использования
```

## 📋 Волшебный промпт

### 📄 Генератор README
> Ожидаемый эффект: профессиональный README проекта, новички быстро вникают

````
## Роль
Ты — инженер по технической документации: пишешь документацию проектов, понятную с первого взгляда.

## Задача
Создать для проекта профессиональный README.md.

## Входные данные
### Обязательные
- Название проекта: 【название】
- Описание одной фразой: 【описание】
- Технологический стек: 【стек】

### Необязательные
- Целевая аудитория: 【кто будет пользоваться проектом?】
- Структура проекта: @explore или [вставьте структуру проекта]

## Формат вывода
Включи разделы:
1. **Заголовок проекта и Badge**
2. **Описание проекта** (3–5 предложений)
3. **Возможности** (списком)
4. **Быстрый старт**
   - Требования к окружению
   - Шаги установки (копипаст и запуск)
   - Команды запуска
5. **Описание настроек** (переменные окружения, конфиги)
6. **API-документация** (если применимо)
7. **Частые вопросы**
8. **Руководство для контрибьюторов**
9. **Лицензия**

## Ограничения
- ✅ Команды быстрого старта — копипаст и запуск
- ✅ Описание настроек — полное, со всеми обязательными пунктами
- ✅ Уместные Badge (статус сборки, версия и т. д.)
- ❌ Без лишней многословности, держи краткость
- ❌ Без пропусков ключевых настроек
````

### 🔧 Генератор сообщений Commit
> Ожидаемый эффект: сообщения в формате Conventional Commits

```
## Роль
Ты — эксперт по кодовым конвенциям: пишешь нормальные сообщения Commit.

## Задача
По изменениям кода создать сообщение коммита по спецификации Conventional Commits.

## Входные данные
### Обязательные
- Содержание изменений: !git diff или [описание изменений]

### Необязательные
- Связанный Issue: 【номер Issue?】

## Формат вывода
Формат: `<type>(<scope>): <description>`

### Выбор type
- feat: новая функция
- fix: исправление бага
- docs: обновление документации
- style: форматирование кода (без влияния на логику)
- refactor: рефакторинг (не функция и не фикс)
- test: всё про тесты
- chore: сборка/инструменты/зависимости

### Нормы
- description — не длиннее 50 символов
- Повелительное наклонение (add, fix, update — не added, fixed)
- Сложное изменение — добавь body с деталями
- Есть связанный Issue — в footer добавь `Closes #123`

## Ограничения
- ✅ type точно отражает тип изменения
- ✅ description конкретный — что именно изменено
- ❌ Без туманных «fix bug» и «update code»
- ❌ Без повтора type в description
```

### 📝 Генератор описаний PR
> Ожидаемый эффект: ясное описание PR, ревьюеру легко понять изменения

````
## Роль
Ты — эксперт по техническому письму: пишешь ясную техническую документацию.

## Задача
По истории коммитов создать описание PR.

## Входные данные
### Обязательные
- История Commit: !git log --oneline -10 или [список коммитов]

### Необязательные
- Цель PR: 【какую проблему решает этот PR?】
- Связанный Issue: 【номер Issue?】

## Формат вывода
```markdown
## Обзор изменений
(цель этого PR одной фразой)

## Детали изменений
- Деталь 1
- Деталь 2
- ...

## Как тестировалось
- [ ] Юнит-тесты зелёные
- [ ] Интеграционные тесты зелёные
- [ ] Ручное тестирование пройдено

## Скриншоты/записи
(если есть UI-изменения — приложите)

## Связанные Issue
Closes #【номер Issue】

## На что обратить внимание ревьюеру
(места, требующие особого внимания)
```

## Ограничения
- ✅ Обзор — цель одной фразой
- ✅ Детали конкретные, а не копия сообщений коммитов
- ✅ UI-изменения — с напоминанием о скриншотах
- ❌ Без пропусков связанных Issue
- ❌ Без слишком общих деталей
````

## Типичные проблемы

| Симптом | Причина | Решение |
|-----|-----|-----|
| README неточный | AI разобрал не всё | Сначала дайте AI понять проект через @explore |
| Формат commit не тот | Не задали конвенцию | Явно требуйте Conventional Commits |
| После /undo сообщение изменилось, а файлы не восстановились | Проект не Git-репозиторий или задан `snapshot: false` | Работайте в Git-репозитории со включёнными снапшотами |
