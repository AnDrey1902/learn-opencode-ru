## Основная идея

### Безопасный рефакторинг в три шага

```
1. Сначала тесты → 2. Маленькие шаги рефакторинга → 3. Тесты зелёные
```

### Запахи кода: краткий обзор

| Запах | Симптомы (опытные сигналы) | Направление рефакторинга |
|-------|----------------|---------|
| Слишком длинная функция | Не охватывается взглядом, делает несколько дел | Выделить функции / разделить обязанности |
| Слишком много параметров | Вызывающий не помнит смысл каждого | Объект параметров / разделить функцию |
| Дублирующийся код | Похожая логика в нескольких местах | Выделить общую функцию |
| Глубокая вложенность | Чтение требует откатов по условиям | Ранний возврат / выделить проверки |
| Непонятные имена | По имени не понять назначение | Переименовать |

## Повторите за мной

<AdInArticle />

### Шаг 1: найдите запахи кода

**Зачем**
Сначала диагноз, потом лечение.

Переключитесь на Plan Agent:

```
@src/utils/data.ts проанализируй качество кода этого файла:
1. Перечисли найденные «запахи»
2. Серьёзность каждой проблемы (высокая/средняя/низкая)
3. Рекомендуемый способ рефакторинга
4. Приоритеты рефакторинга
```

### Шаг 2: сначала сгенерируйте тесты

**Зачем**
Без тестов безопасного рефакторинга не бывает.

Переключитесь на Build Agent:

```
@src/utils/data.ts сгенерируй юнит-тесты для этого файла:
1. Фреймворк Vitest
2. Покрой все экспортируемые функции
3. Включи обычные и граничные случаи
4. Сохрани в src/utils/data.test.ts
```

### Шаг 3: безопасно отрефакторите

**Зачем**
Маленькие шаги, каждый с проверкой.

```
@src/utils/data.ts отрефактори функцию parseUserData:
- Проблема: функция длинная (50 строк), обязанностей несколько
- Требование: разбить на 3 маленькие функции
- Публичный интерфейс не менять
- После рефакторинга прогнать тесты
```

### Шаг 4: добейте граничные тесты

**Зачем**
Граничные условия — главный рассадник багов.

```
@src/utils/data.ts @src/utils/data.test.ts

Разбери граничные условия кода и допиши тесты:
1. Пустой ввод (null, undefined, пустой массив)
2. Экстремумы (огромные числа, сверхдлинные строки)
3. Ошибки типов (передан неверный тип)
4. Конкуренция (если есть асинхронность)
```

### Шаг 5: прогоните тесты

**Зачем**
Убедиться, что рефакторинг ничего не сломал.

> В OpenCode TUI сообщение с `!` в начале выполняет shell-команду и подтягивает вывод в диалог: https://opencode.ai/docs/tui

```
!npm test src/utils/data.test.ts
```

**Вы должны увидеть**: все тесты зелёные

## 📋 Волшебный промпт

### ✅ Ревью кода
> Ожидаемый эффект: полный разбор проблем качества кода с рекомендациями

```
## Роль
Ты — техлид, отвечаешь за качество кода. Стиль ревью — строгий, но конструктивный.

## Задача
Провести полное ревью присланного кода: найти проблемы и дать рекомендации.

## Входные данные
### Обязательные
- Язык программирования: 【язык】
- Код: @【путь к файлу】 или [вставьте код]

### Необязательные
- Фокус проверки: 【на что обратить внимание?】
- Контекст проекта: 【контекст кода?】

## Направления проверки
1. **Качество кода**: именование, структура, читаемость, дубли
2. **Потенциальные проблемы**: риски багов, граничные условия, обработка ошибок, производительность
3. **Угрозы безопасности**: валидация ввода, чувствительные данные, риски инъекций
4. **Лучшие практики**: паттерны проектирования, принципы SOLID, покрытие тестами

## Формат вывода
### Итог ревью
- **Оценка кода**: A (отлично) / B (хорошо) / C (средне) / D (нужен рефакторинг)
- **Оценка одной фразой**
- **Править перед мерджем**: да/нет

### Список проблем
- 🔴 **Серьёзные**: `[файл:строка]` проблема + риск + рекомендация
- 🟡 **Желательно исправить**: рекомендованные проблемы
- 🟢 **Плюсы**: что стоит сохранить

## Ограничения
- ✅ Проблемы — конкретно до строк
- ✅ К каждой проблеме — рекомендация
- ✅ Отмечай сильные места
- ❌ Не подменяй объективные критерии вкусовщиной
- ❌ Не критикуй без предложений
```

### 🧪 Генерация тестов
> Ожидаемый эффект: полные юнит-тесты с граничными условиями

```
## Роль
Ты — QA-инженер: проектируешь всесторонние тест-кейсы, покрываешь обычные сценарии и границы.

## Задача
Сгенерировать юнит-тесты для присланной функции или модуля.

## Входные данные
### Обязательные
- Язык программирования: 【язык】
- Код: @【путь к файлу】 или [вставьте код]

### Необязательные
- Тестовый фреймворк: 【Jest/Vitest/Pytest/JUnit?】 (по умолчанию: определить сам)
- Стиль тестов: 【BDD-стиль describe/it?】

## Формат вывода
Используй паттерн AAA (Arrange-Act-Assert), покрой:
1. **Обычный сценарий** (Happy Path)
2. **Граничные условия** (пустые, экстремумы, пороги)
3. **Нештатные ситуации** (неверный ввод, исключения)
4. **Асинхронность** (если есть Promise/async)

Каждый тест-кейс включает:
- Понятное имя (что проверяет)
- Нужные комментарии (какой сценарий)

## Ограничения
- ✅ Имена тестов ясно выражают намерение
- ✅ Главные граничные условия покрыты
- ✅ Тесты запускаются как есть
- ❌ Не тестируй детали реализации
- ❌ Тест-кейсы не должны зависеть друг от друга
```

### 🔧 Рекомендации по рефакторингу
> Ожидаемый эффект: безопасный план рефакторинга с низкими рисками

```
## Роль
Ты — эксперт по рефакторингу: находишь запахи кода и даёшь безопасные планы.

## Задача
Разобрать проблемы кода, дать безопасные шаги и рекомендации.

## Входные данные
### Обязательные
- Код: @【путь к файлу】 или [вставьте код]

### Необязательные
- Известные проблемы: 【что заметили?】
- Цель рефакторинга: 【чего хотите добиться?】

## Формат вывода
1. **Разбор текущих проблем**
   - Найденные запахи (длинная функция/лишние параметры/глубокая вложенность/дубли/плохие имена)
   - Серьёзность каждой (высокая/средняя/низкая)

2. **Рекомендуемые шаги** (по порядку)
   - Что делать на каждом шаге
   - Оценка риска шага
   - Как проверить успех шага

3. **Какие тесты нужны**
   - Какие тесты должны быть до рефакторинга
   - Какие добавить после

4. **Ожидаемый эффект**
   - В чём вырастет качество кода
   - Что улучшится в поддерживаемости

## Ограничения
- ✅ Маленькие шаги, каждый проверяем
- ✅ Публичный интерфейс не меняем
- ✅ Сначала тесты, потом рефакторинг
- ❌ Не менять слишком много за раз
- ❌ Не менять бизнес-логику
```

## Типичные проблемы

| Симптом | Причина | Решение |
|-----|-----|-----|
| После рефакторинга всё сломалось | Сначала не написали тесты | Сначала генерируйте тесты, потом рефакторите |
| Покрытие низкое | Тестируете только обычные случаи | Добавьте граничные и негативные тесты |
| Запахи определяются неточно | Дали слишком маленький фрагмент | Давайте AI полный контекст файла |
