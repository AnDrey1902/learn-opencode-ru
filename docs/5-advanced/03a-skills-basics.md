# 5.3a Основы Skill

> Skill — пакет экспертных знаний с **подгрузкой по требованию**: определяется через SKILL.md, Agent сам находит и подгружает его по смыслу задачи.

## 📝 Конспект урока

Ключевые идеи урока в сжатом виде:

<details>
<summary>📝 Текстовая версия шпаргалки</summary>

1. Зачем Skill: Claude стартует с нуля — не знает структуру таблиц, нормы команд, бизнес-определения.
2. Три слоя раскрытия: Layer 1 name+desc (видно всегда) → Layer 2 SKILL.md (при совпадении) → Layer 3 references/ (по необходимости).
3. Skill против CLAUDE.md: Skill = по необходимости + кросс-проект + код; CLAUDE.md = всегда + текущий проект + Markdown.
4. Структура: `.opencode/skill/sql-analysis/SKILL.md` + `references/` (finance.md, product.md, examples.md).
5. Поиск: проектные `.opencode/skill/`, `.claude/skills/`; глобальные `~/.config/opencode/skill/`, `~/.claude/skills/`.
6. Права: `"permission": {"skill": {"*": "ask", "sql-*": "allow"}}`.
7. Ловушки: SKILL.md не грузится — регистр; Skill не появляется — нет name/desc; конфликты — одно имя в нескольких местах.

## Зачем нужны Skill

### В чём трудность

```
Пользователь: помоги запросить данные о выручке из хранилища

Claude: предлагаю такой SQL-запрос...
SELECT * FROM revenue WHERE date > '2024-01-01'
```

Claude даёт общий SQL-шаблон, но не знает:
- как устроены ваши таблицы
- как «выручка» определяется в компании
- что нужно исключать тестовые аккаунты
- какую витрину использовать

**Корень проблемы**: каждый диалог Claude начинает с чистого листа — знаний вашей команды у него нет.

### Как решает Skill

```
Пользователь: помоги запросить данные о выручке из хранилища

Claude: [автоматически подгружает Skill sql-analysis]
Помогу запросить данные о выручке. По вашим нормам данных:
- используем витрину monthly_revenue
- исключаем тестовые аккаунты (account != 'Test')
- выручка считается как ARR (monthly * 12)

SELECT ...
```

Skill упаковывает ваши экспертные знания в ресурс, который Claude вызывает по мере необходимости.

## Главная дизайн-идея Skill

### Постепенное раскрытие (Progressive Disclosure)

Skill не пихает всё содержимое в контекст, а **подгружает слоями**:

```
┌─────────────────────────────────────────────────────────┐
│ Слой 1: name + description (~100 слов)                  │
│ → виден всегда, по нему решается нуждаемость             │
├─────────────────────────────────────────────────────────┤
│ Слой 2: тело SKILL.md                                   │
│ → грузится при совпадении задачи, главные инструкции     │
├─────────────────────────────────────────────────────────┤
│ Слой 3: подробные документы в каталоге references/      │
│ → только когда нужны конкретные детали                   │
└─────────────────────────────────────────────────────────┘
```

**Зачем так устроено?**

Окно контекста — ценный ресурс. Запихать туда все экспертные знания — получишь:
- огромный расход токенов
- рассеянное внимание модели
- нерелевантный контент мешает выводу

Постепенное раскрытие грузит Claude только то, что нужно текущей задаче.

### Skill vs CLAUDE.md

| Характеристика | CLAUDE.md | Skill |
|------|-----------|-------|
| **Момент загрузки** | Всегда в контексте | Только при совпадении задачи |
| **Область применения** | Текущий проект | Переиспользование между проектами |
| **Тип содержимого** | Чистый Markdown | Markdown + код + файлы ресурсов |
| **Поддержка платформами** | Только Claude Code и OpenCode | Claude.ai, Code и API |
| **Типичное применение** | Нормы проекта, локальные команды | Экспертиза предметной области, процессы |

**Принципы выбора**:
- Нормы конкретного проекта (стиль кода, именование веток) → CLAUDE.md
- Переиспользуемые экспертные знания (процессы анализа данных, нормы аудита) → Skill

## Структура каталогов Skill

### Базовая структура

```
.opencode/
└── skill/
    └── code-review/
        └── SKILL.md      # Файл определения навыка (обязательно капсом)
```

### Рекомендуемая полная структура

```
.opencode/
└── skill/
    └── sql-analysis/
        ├── SKILL.md              # Главный файл: процесс и главная логика
        └── references/           # Подробные документы (подгрузка по требованию)
            ├── finance.md        # Структура финансовых таблиц
            ├── product.md        # Структура продуктовых таблиц
            └── examples.md       # Примеры запросов
```

**Принцип**: SKILL.md — сжато, детали — в references/, Claude прочитает при необходимости.

### Где ищет OpenCode

| Место | Область | Пояснение |
|-----|---------|------|
| `.opencode/skill/<name>/SKILL.md` | Текущий проект | Навыки проекта |
| `~/.config/opencode/skill/<name>/SKILL.md` | Глобально | Доступны всем проектам |
| `.claude/skills/<name>/SKILL.md` | Текущий проект | Формат совместимости с Claude |
| `~/.claude/skills/<name>/SKILL.md` | Глобально | Формат совместимости с Claude |

> Пути проекта обходятся от текущего каталога вверх до корня git.

### references проекта — не `references/` навыка

Каталог `references/` внутри Skill — просто его собственная договорённость о каталоге материалов. Ключ `references` верхнего уровня в `opencode.json` — другая возможность: регистрирует локальные каталоги или Git-репозитории как контекст проекта.

```jsonc
{
  "references": {
    "backend": {
      "path": "../backend",
      "description": "Исходники бэкенд-сервиса"
    },
    "design-system": {
      "repository": "https://github.com/example/design-system.git",
      "branch": "main",
      "description": "Компоненты и нормы дизайна",
      "hidden": true
    }
  }
}
```

- Локальные пункты — через `path`; Git-пункты — через `repository`, необязательно `branch`.
- При наличии `description` reference попадает в системный контекст; `hidden: true` лишь прячет его из `@`-дополнения TUI.
- Используйте множественный ключ `references`. Единственное `reference` в `v1.18.22` ещё совместимо, но уже deprecated.

Schema: [`reference.ts:5-21`](https://github.com/anomalyco/opencode/blob/v1.18.22/packages/core/src/config/reference.ts#L5-L21), инжект в системный контекст: [`system.ts:69-92`](https://github.com/anomalyco/opencode/blob/v1.18.22/packages/opencode/src/session/system.ts#L69-L92), логика скрытия в TUI: [`autocomplete.tsx:423-439`](https://github.com/anomalyco/opencode/blob/v1.18.22/packages/tui/src/component/prompt/autocomplete.tsx#L423-L439).

::: info Свой каталог конфигурации
Через переменную окружения `OPENCODE_CONFIG_DIR` задаются дополнительные пути поиска Skill:

```bash
export OPENCODE_CONFIG_DIR="/path/to/custom/config"
```

OpenCode одновременно сканирует:
- Каталог конфигурации по умолчанию: `~/.config/opencode/skill/`
- Пользовательский каталог конфигурации: `$OPENCODE_CONFIG_DIR/skill/`

Удобно для общих командных Skill или разных наборов под разные окружения.

`v1.18.22` забирает все каталоги конфигурации из сервиса конфигурации и сканирует в них `{skill,skills}/**/SKILL.md` (исходники: [`skill/index.ts:205-208`](https://github.com/anomalyco/opencode/blob/v1.18.22/packages/opencode/src/skill/index.ts#L205-L208)).
:::

### Поддержка вложенных каталогов

OpenCode поддерживает вложенные каталоги Skill:

```
.opencode/
└── skill/
    └── audit/
        └── security/
            └── SKILL.md    # имя навыка определяется полем name во frontmatter
```

Доказательства в исходниках: [`skill/index.ts:21-25`](https://github.com/anomalyco/opencode/blob/v1.18.22/packages/opencode/src/skill/index.ts#L21-L25)
```typescript
const OPENCODE_SKILL_PATTERN = "{skill,skills}/**/SKILL.md"
```

`**` покрывает подкаталоги любой глубины.

### Встроенный Skill `customize-opencode`

В `v1.18.22` по умолчанию зарегистрирован `customize-opencode` для изменения собственных конфигурации OpenCode, Agent, Skill, плагинов, MCP и прав. Он регистрируется раньше дисковых Skill, поэтому одноимённый локальный Skill перекрывает встроенную версию (исходники: [`skill/index.ts:27-35`](https://github.com/anomalyco/opencode/blob/v1.18.22/packages/opencode/src/skill/index.ts#L27-L35),[`skill/index.ts:276-284`](https://github.com/anomalyco/opencode/blob/v1.18.22/packages/opencode/src/skill/index.ts#L276-L284)).

::: info Scout — историческая возможность, не текущий Agent
Scout когда-то добавляли в синхронизируемом диапазоне, но в `v1.16.0` удалили. Не опирайтесь на Scout в списке Agent `v1.18.22` и процессах; для исследования кодовой базы используйте видимых сейчас Agent и инструменты.

## Формат SKILL.md

<AdInArticle />

### Обязательный Frontmatter

```yaml
---
name: sql-analysis
description: Для анализа бизнес-данных: выручка, ARR, сегментация клиентов, использование продукта, воронка продаж. Даёт структуры таблиц, определения метрик, обязательные фильтры и шаблоны запросов.
---
```

| Поле | Обязательно | Описание |
|-----|------|------|
| `name` | Да | Идентификатор навыка для вызова |
| `description` | Да | Описание условий срабатывания (**самое важное!**) |
| `license` | Нет | Информация о лицензии |
| `compatibility` | Нет | Метки совместимости |
| `metadata` | Нет | Пользовательские пары ключ-значение |

### Нормы именования name

Официально рекомендуются нормы (исходники не валидируют строго, но следуйте ради совместимости):

```
✓ code-review
✓ sql-analysis
✓ git-release
✗ Code_Review    ← без заглавных
✗ sql--analysis  ← без двойных дефисов
✗ -review        ← не начинать с дефиса
```

Референс регулярки: `^[a-z0-9]+(-[a-z0-9]+)*$`

### Написание description (решает срабатывание)

description — **единственный фактор срабатывания** Skill. Claude понимает смысл (а не совпадение ключевых слов) и решает, нужна ли Skill задаче.

**Плохое написание**:
```yaml
description: Помогает обрабатывать документы
```
Проблема: туманно, AI не понимает, когда срабатывать.

**Хорошее написание**:
```yaml
description: |
  Извлекает таблицы из PDF и конвертирует в формат CSV для аналитических процессов.
  Применимо: заполнение PDF-форм, пакетная обработка PDF-документов, извлечение встроенных данных PDF.
  Неприменимо: простой просмотр PDF, базовая конвертация форматов, редактирование PDF.
```

**Шаблон написания description**:
```yaml
description: |
  [Одна фраза о главной способности]
  Даёт: [ресурсы навыка: структуры таблиц, формулы, шаблоны]
  Применимо: [сценарий срабатывания 1], [сценарий 2], [сценарий 3]
  Неприменимо: [граничный сценарий 1], [граничный сценарий 2]
```

**Элементы description**:
1. **Конкретная способность**: что умеет (извлекать таблицы, конвертировать форматы)
2. **Даваемые ресурсы**: что внутри (структуры таблиц, формулы, шаблоны)
3. **Сценарии срабатывания**: когда применять (пакетная обработка, заполнение форм)
4. **Границы**: когда не применять (простой просмотр)

### Полный пример

```markdown
---
name: sql-analysis
description: |
  Для анализа бизнес-данных: тренды выручки, расчёт ARR, сегментация клиентов, использование продукта, воронка продаж.
  Даёт: структуры таблиц компании, формулы определения метрик, стандартные фильтры, шаблоны частых запросов.
  Применимо: нужно писать SQL для анализа бизнес-данных, понимать определения метрик компании, запрашивать хранилище.
  Неприменимо: администрирование баз данных, DDL-операции, тюнинг производительности, общее обучение SQL.
---

# Навык SQL-анализа

## Быстрый процесс

Когда пользователь просит анализ данных:

1. **Уточните потребность**
   - Какой временной диапазон? (по умолчанию текущий год)
   - Какая сегментация клиентов?
   - Для какого решения этот анализ?

2. **Проверьте существующие дашборды**
   - Посмотрите, нет ли готового отчёта в `references/dashboards.md`
   - Если есть — сначала направьте пользователя туда

3. **Определите источник данных**
   - Предпочитайте витрины сырым событийным данным
   - Перед запросом убедитесь, что в таблице есть нужные поля

4. **Выполните анализ**
   - Примените обязательные фильтры (исключение тестовых аккаунтов и т. д.)
   - Сверьте результат с известными бенчмарками

## Стандартные фильтры запросов

Все запросы выручки обязаны:
- Исключать тестовые аккаунты: `WHERE account != 'Test'`
- Брать только полные периоды: `WHERE month <= DATE_TRUNC(CURRENT_DATE(), MONTH)`

## Способ расчёта ARR

- Месячная выручка в ARR: `monthly_revenue * 12`
- 7-дневная скользящая годовая: `rolling_7d * 52`

## Подробная документация

Структуры таблиц и шаблоны запросов — по ссылкам:
- **Выручка и финансы** → `references/finance.md`
- **Использование продукта** → `references/product.md`
- **Воронка продаж** → `references/sales.md`
```

Обратите внимание: SKILL.md содержит только процесс и главную логику, детальные структуры таблиц лежат в каталоге references/.

## Как Skill обнаруживаются и загружаются

### Механизм обнаружения

При старте OpenCode сканирует все Skill и сводит name и description в описание инструмента `skill`:

```xml
<available_skills>
  <skill>
    <name>sql-analysis</name>
    <description>Для анализа бизнес-данных: выручка, ARR, сегментация клиентов...</description>
  </skill>
  <skill>
    <name>code-review</name>
    <description>Выполняет ревью кода: проверяет нормы, баги, производительность и безопасность</description>
  </skill>
</available_skills>
```

### Механизм загрузки

Когда пользователь отправляет сообщение, Claude по смыслу решает, грузить ли Skill:

```
Сообщение пользователя: проанализируй выручку прошлого квартала

Claude решает: задача аналитическая, совпадает со Skill sql-analysis

Claude вызывает: skill({ name: "sql-analysis" })

Результат: содержимое SKILL.md загружается в контекст
```

### Вывод после загрузки

```
## Skill: sql-analysis

**Base directory**: /path/to/.opencode/skill/sql-analysis

[содержимое SKILL.md]
```

Информация `Base directory` подсказывает Claude, как обращаться к относительным путям файлов в references/.

## Настройка прав

### Глобальные права

Настройка в `opencode.json`:

```jsonc
{
  "permission": {
    "skill": {
      "pr-review": "allow",        // Грузить сразу
      "internal-*": "deny",        // Скрыть, доступ запретить
      "experimental-*": "ask",     // Перед загрузкой спросить пользователя
      "*": "allow"                 // Остальное по умолчанию разрешить
    }
  }
}
```

| Значение права | Поведение |
|--------|------|
| `allow` | Skill грузится сразу |
| `deny` | Skill скрыт от Agent, доступ запрещён |
| `ask` | Перед загрузкой просит подтверждения пользователя |

> Поддерживаются wildcard: `internal-*` покрывает `internal-docs`, `internal-tools` и т. д.

### Переопределение прав для отдельных Agent

**В Markdown Agent**:

```yaml
---
permission:
  skill:
    "documents-*": "allow"
---
```

**В opencode.json**:

```jsonc
{
  "agent": {
    "plan": {
      "permission": {
        "skill": {
          "internal-*": "allow"
        }
      }
    }
  }
}
```

### Полное отключение инструмента Skill

Для Agent, которым Skill не нужен, отключите полностью:

**Способ Markdown**:

```yaml
---
tools:
  skill: false
---
```

**Способ JSON**:

```jsonc
{
  "agent": {
    "plan": {
      "tools": {
        "skill": false
      }
    }
  }
}
```

После отключения раздел `<available_skills>` полностью исчезнет из описания инструментов этого Agent.

## Типичные проблемы

| Симптом | Причина | Решение |
|-----|-----|-----|
| Skill не грузится | Регистр SKILL.md неверный | Обязательно капсом `SKILL.md` |
| Skill не виден | Во frontmatter не хватает полей | Обязательны `name` и `description` |
| Задача совпала, но не срабатывает | description туманный | Добавьте конкретные способности, сценарии и границы |
| Конфликт одноимённых Skill | Определены в нескольких местах | Позже загруженный перекрывает ранее загруженный, смотрите предупреждения в логах |
| Доступ запрещён | Права выставлены в deny | Проверьте конфигурацию permission |
| Каталог Skill не распознаётся | Опечатка в имени каталога | Поддерживаются `skill/` и `skills/` |
