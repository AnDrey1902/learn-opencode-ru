## Трёхуровневая структура постепенного раскрытия

### Зачем нужны слои

Представьте, что ваш Skill содержит:
- Детальные структуры 10 таблиц
- 50 частых примеров запросов
- Разборы всевозможных краевых случаев

Запихать всё это в SKILL.md — получишь:
- мгновенно исчерпанное окно контекста
- рассеянное внимание модели
- взлетевшие счета за токены

**Решение**: организуйте Skill как справочник:

```
Оглавление (видно всегда) → главы (читаются по мере нужды) → приложения (справка по требованию)
```

### Три слоя подробно

<AdInArticle />

```
skill/
└── sql-analysis/
    ├── SKILL.md                    # Слой 2: главный процесс
    └── references/                 # Слой 3: подробные документы
        ├── finance.md              # Структура финансовых таблиц
        ├── product.md              # Структура продуктовых таблиц
        ├── sales.md                # Структура таблиц продаж
        └── examples/
            ├── revenue-queries.md  # Примеры запросов выручки
            └── churn-queries.md    # Примеры анализа оттока
```

**Слой 1**: name + description (~100 слов)
- Всегда загружен в `<available_skills>`
- По нему решается нуждаемость в загрузке Skill

**Слой 2**: тело SKILL.md
- Загружается при совпадении задачи
- Содержит процесс, главную логику, дерево решений
- Держите сжато (рекомендуется 300–2000+ слов)

**Слой 3**: каталог references/
- Только когда нужны конкретные детали
- Claude читает файлы по мере необходимости
- Сюда — сколько угодно подробностей

### Пример реализации

**SKILL.md (слой 2)**:

```markdown

### Зачем нужны скрипты

Отдельные действия кодом выполняются эффективнее и надёжнее генерации токенами:

# Навык обработки PDF

## Извлечение полей форм

PDF в контекст грузить не нужно, запускайте скрипт напрямую:

```bash
python scripts/extract_form_fields.py input.pdf
```

Пример вывода:
```json
{
  "fields": [
    {"name": "full_name", "type": "text", "value": ""},
    {"name": "date", "type": "date", "value": ""}
  ]
}
```

## Слияние нескольких PDF

```bash
python scripts/merge_pdfs.py file1.pdf file2.pdf -o output.pdf
```

## Конвертация в картинки

```bash
python scripts/convert_to_images.py document.pdf --output-dir ./images
```

Подробности параметров — в `references/scripts-guide.md`.
```

### Принципы написания скриптов

1. **Автономность**: скрипт выполняется сам, без сложного окружения
2. **Ясные вход и выход**: понятные параметры и формат возврата
3. **Обработка ошибок**: изящно разбирать нештатные ситуации
4. **Минимум зависимостей**: только нужные библиотеки

**Пример скрипта** (`scripts/extract_form_fields.py`):

```python
#!/usr/bin/env python3
"""Извлечение информации о полях PDF-форм"""

import sys
import json

def extract_fields(pdf_path: str) -> dict:
    """Извлечь поля формы из PDF"""
    try:
        # Используем PyPDF2 или другую библиотеку
        from pypdf import PdfReader
        reader = PdfReader(pdf_path)
        fields = reader.get_fields() or {}
        
        result = []
        for name, field in fields.items():
            result.append({
                "name": name,
                "type": str(field.get("/FT", "unknown")),
                "value": str(field.get("/V", ""))
            })
        
        return {"fields": result, "count": len(result)}
    
    except Exception as e:
        return {"error": str(e)}

if __name__ == "__main__":
    if len(sys.argv) < 2:
        print(json.dumps({"error": "Usage: extract_form_fields.py <pdf_path>"}))
        sys.exit(1)
    
    result = extract_fields(sys.argv[1])
    print(json.dumps(result, indent=2, ensure_ascii=False))
```

## Процесс создания из 5 шагов

### Шаг 1: проясните потребность

Прежде чем писать что-либо, ответьте на вопросы:

| Вопрос | Зачем |
|------|------|
| Какую конкретную проблему решает Skill? | Прояснить ценность |
| Когда должен срабатывать? | Спроектировать description |
| Как выглядит успешный вывод? | Определить критерии приёмки |
| Какие краевые случаи? | Ничего не упустить |

**Хорошие кандидаты в сценарии**:
- Знания, переиспользуемые между проектами
- Процессы, нужные нескольким людям
- Стабильные редко меняющиеся паттерны

**Не годятся в Skill**:
- Разовые задачи
- Часто меняющееся содержимое
- Нормы конкретных проектов (им место в CLAUDE.md)

### Шаг 2: напишите name

```yaml
name: sql-analysis
```

Принципы именования:
- Коротко и ясно
- Строчные буквы и цифры
- Разделитель — одиночный дефис
- Отражает главную функцию

### Шаг 3: напишите description (самое важное)

description решает срабатывание — главная часть.

**Плохой description**:

```yaml
description: Помогает обрабатывать данные
```

Проблема: туманно — что считается «обработкой данных»?

**Хороший description**:

```yaml
description: Извлекает таблицы из PDF и конвертирует в формат CSV для аналитических процессов. Применяется при заполнении PDF-форм и пакетной обработке PDF-документов. Не применяется для простого просмотра PDF и базовой конвертации форматов.
```

**Чек-лист элементов description**:

| Элемент | Пример |
|------|------|
| Конкретная способность | «Извлекать таблицы и конвертировать в CSV» |
| Сценарий срабатывания | «Когда нужно заполнять PDF-формы» |
| Объект использования | «Для аналитических процессов» |
| Граничные ограничения | «Не для простого просмотра PDF» |

### Шаг 4: напишите главные инструкции

Структурированно, сканируемо, применимо:

```markdown
# Навык SQL-анализа

## Процесс

1. **Уточните потребность**
   - Временной диапазон? (по умолчанию текущий год)
   - Сегментация клиентов?
   - Для какого решения?

2. **Выберите источник данных**
   - Предпочитайте витрины
   - Убедитесь в наличии нужных полей

3. **Выполните запрос**
   - Примените стандартные фильтры
   - Проверьте разумность результата

## Стандартные фильтры

Все запросы обязаны включать:
- `WHERE account_id != 'Test'`
- `WHERE month <= DATE_TRUNC(CURRENT_DATE(), MONTH)`

## Подробная документация

- Структуры таблиц → `references/tables.md`
- Примеры запросов → `references/examples.md`
```

**Принципы написания**:

| Принцип | Описание |
|------|------|
| Структура Markdown | Заголовки, списки и таблицы добавляют читаемости |
| Конкретные примеры | Блоки кода показывают верное использование |
| Опишите запреты | Во избежание неверного применения |
| Ссылайтесь на подробные документы | Главный файл держите сжатым |

### Шаг 5: протестируйте и проверьте

Системно тестируйте Skill — убеждайтесь в работе во всех сценариях.

#### Матрица тестов

| Тип теста | Что тестируется | Ожидаемый результат | Приоритет |
|---------|---------|---------|-------|
| **Тест срабатывания** | «Проанализируй выручку прошлого квартала» | Skill активируется | P0 |
| **Граничный тест** | «Выручка» (без временного диапазона) | Спросит и выполнит | P1 |
| **Негативный тест** | «Напиши мне письмо» | Не активируется | P0 |
| **Тест вывода** | Формат вывода по стандарту | Формат верный | P1 |
| **Тест ошибок** | Намеренно неверные параметры | Изящная ошибка | P2 |

#### Тест срабатывания

```
# ✅ Запросы, которые обязаны сработать
"Используя навык sql-analysis, проанализируй данные" → явный запрос, обязан сработать
"Посмотри изменение ARR за прошлый квартал" → естественный запрос, семантическое совпадение
"Анализ трендов выручки" → совпадение по ключевым словам, обязан сработать

# ❌ Запросы, которые не обязаны срабатывать
"Напиши мне SQL-учебник" → это обучение, не анализ
"Тюнинг производительности базы" → вне границ (в description сказано: неприменимо)
"Создай новую таблицу" → DDL-операции, неприменимо
```

#### Функциональные тесты

| Что проверяется | Как тестировать | Критерий прохождения |
|--------|---------|---------|
| Консистентность вывода | Один вход прогнать 3 раза | Ядро содержания совпадает |
| Доступность новичкам | Дать попробовать незнакомому с областью | Задачу выполняет успешно |
| Точность документации | Действовать по примерам | Результат совпадает с примером |
| Полнота ссылок | Проверить пути references/ | Все ссылки существуют |

#### Тестовый скрипт (необязательно)

Создайте `.opencode/skill/<name>/test.sh`:

```bash
#!/bin/bash
# Скрипт автотестов Skill

echo "=== Тесты срабатывания ==="
# Тест 1: нормальное срабатывание
opencode --prompt "Проанализируй выручку прошлого квартала" --check-skill "sql-analysis"

# Тест 2: негативный тест
opencode --prompt "Напиши мне письмо" --expect-no-skill "sql-analysis"

echo "=== Функциональные тесты ==="
# Тест формата вывода
opencode --prompt "Проанализируй ARR" | grep -q "## Расчёт ARR" && echo "✅ Формат вывода верный"
```

#### Чек-лист тестирования

После этих проверок Skill готов к бою:

- [ ] **Тесты срабатывания**: 3 позитивных кейса активируются
- [ ] **Негативные тесты**: 3 граничных кейса не активируются
- [ ] **Тесты вывода**: формат вывода соответствует ожиданиям
- [ ] **Тесты новичками**: непрофессионал успешно пользуется
- [ ] **Тесты ссылок**: все файлы references/ существуют
- [ ] **Тесты ошибок**: на неверный ввод — понятные подсказки

```

### Учиться на сбоях

Когда выполнение Skill ошибается:

```
Пользователь: результат запроса неверный — тестовые аккаунты не исключены

Claude: давай разберусь в проблеме:
1. Стандартный фильтр не применился
2. Возможно, инструкция недостаточно явная

Предлагаю обновить SKILL.md:
- В разделе «Обязательные фильтры» выделить жирным
- Добавить предупреждение «категорически нельзя пропускать»
```

Закрепляйте такие выводы в Skill.

### Постоянная оптимизация

```
1. Используйте Skill в работе
2. Записывайте успешные паттерны и случаи сбоев
3. Регулярно пересматривайте и обновляйте Skill
4. Делитесь с командой
```

# Создание, правка и анализ DOCX

### Чтение и анализ содержимого
Используйте разделы «Извлечение текста» или «Доступ к сырому XML» ниже

Используйте процесс «Создание нового Word-документа»

### Правка существующего документа

- **Чужой документ**: используйте **процесс ревизий** (рекомендуется по умолчанию)

# Навык дизайна фронтенда

## Дизайн-мышление

Перед кодом поймите контекст и выберите **смелое эстетическое направление**:

- **Цель**: какую проблему решает интерфейс? Кто пользуется?
- **Стиль**: выберите крайность: минимализм, максимализм, ретрофутуризм, природная органика, роскошь, игрушечность, журнальная вёрстка...
- **Отличие**: что сделает дизайн запоминающимся?

## Гайд фронтенд-эстетики

### Типографика
Выбирайте уникальные шрифты. Никаких Arial, Inter и прочих общих.
Рекомендуются: JetBrains Mono, Playfair Display, IBM Plex, Bricolage Grotesque

### Цвета
Держитесь единой эстетики. Консистентность — через CSS-переменные.
Главный цвет с острым акцентом лучше равномерно размазанной мягкой палитры.

### Движение
Анимации добавляют эффект и микровзаимодействия.
Одна продуманная загрузка страницы (каскадное появление) приятнее россыпи микровзаимодействий.

### Фоны
Создавайте атмосферу и глубину вместо дефолтной заливки.
Градиентные сетки, шумовые текстуры, геометрические паттерны, слои прозрачности.

## Категорически нельзя

- Inter, Roboto, Arial, системные шрифты
- Белый фон с фиолетовым градиентом (фирменная AI-эстетика)
- Предсказуемые раскладки и паттерны компонентов
- Шаблонный дизайн без учёта контекста
```

**Сильные стороны этого Skill**:
- Ясно обозначена проблема (сгенерированная AI типовая эстетика)
- Даны конкретные альтернативы
- Есть список «категорически нельзя»

## Безопасностный аудит

### Зачем нужен аудит

Skill умеют:
- давать Claude инструкции
- содержать исполняемый код
- направлять Claude к сетевым ресурсам

Вредоносный Skill может привести к утечке данных или порче системы.

### Чек-лист безопасностного аудита

| Что проверяется | Содержание проверки | Риск |
|--------|---------|------|
| **Содержимое файлов** | Прочитать все .md-файлы | Подозрительные инструкции? |
| **Код скриптов** | Проверить файлы .py и .js | Вредоносный код? |
| **Сетевые запросы** | Проверить URL и вызовы API | Подключения к недоверенным сервисам? |
| **Зависимости** | Проверить import и require | Вредоносные пакеты? |
| **Файлы ресурсов** | Проверить картинки и файлы данных | Чувствительная информация? |

### Надёжность источников

| Источник | Надёжность | Рекомендация |
|------|--------|------|
| Официальный репозиторий | Высокая | Можно сразу |
| Известные разработчики | Средняя | Быстро проверить и можно |
| Неизвестные источники | Низкая | Полный аудит перед использованием |
| Скачанное из сети | Неизвестна | Осторожно |

### Пример аудита

```bash
# 1. Посмотреть все файлы
find my-skill/ -type f -name "*.md" -o -name "*.py" -o -name "*.js"

# 2. Проверить сетевые запросы
grep -r "http" my-skill/
grep -r "fetch\|requests\|urllib" my-skill/

# 3. Проверить операции с файловой системой
grep -r "open\|write\|delete\|remove" my-skill/

# 4. Проверить зависимости
cat my-skill/requirements.txt
cat my-skill/package.json
```

## Типичные проблемы

| Симптом | Причина | Решение |
|-----|-----|-----|
| Skill срабатывает всегда | description слишком широкий | Добавьте граничные ограничения: «не применяется для X» |
| Skill не срабатывает никогда | description слишком конкретный | Добавьте больше сценариев срабатывания |
| Конфликт нескольких Skill | Пересекающиеся description | Чётко разграничьте обязанности |
| references не грузятся | Неверный путь | Относительные пути вида `references/xxx.md` |
| Скрипты падают | Нет зависимостей | Убедитесь, что окружение с нужными пакетами |
| Вывод нестабилен | Туманные инструкции | Добавьте конкретные примеры и шаги проверки |
| Переполнение контекста | SKILL.md слишком длинный | Разбейте на references/ |

## Итоги урока

Вы научились:

1. **Трёхуровневому постепенному раскрытию**
   - Слой 1: name + description (видно всегда)
   - Слой 2: тело SKILL.md (грузится при совпадении задачи)
   - Слой 3: references/ (грузится по требованию)
2. **Исполняемым скриптам**
   - Подходят для детерминированных действий
   - Лежат в каталоге `scripts/`
   - В SKILL.md описано, как вызывать
3. **Процессу создания из 5 шагов**
   - Прояснить потребность → написать name → написать description → написать инструкции → протестировать
4. **Итеративной разработке**
   - Извлекать знания в паре с Claude
   - Учиться на сбоях и закреплять в Skill
5. **Безопасностному аудиту**
   - Проверять файлы, скрипты, сеть, зависимости
   - Предпочитать надёжные источники
