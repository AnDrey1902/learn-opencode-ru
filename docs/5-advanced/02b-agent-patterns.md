## Главные принципы

Anthropic, построив Agent с десятками команд, вывел три главных принципа:

### 1. Держите простоту

> «Самые успешные реализации — простые компонуемые паттерны, а не сложные фреймворки».

**Практика**:
- Решается одним Agent — не городите нескольких
- Хватает фиксированного процесса — не нужна динамическая логика
- Решается промптом — не добавляйте инструменты

### 2. Приоритет прозрачности

> «Явно показывайте шаги планирования Agent».

**Практика**:
- Ход мыслей Agent видим
- У каждого шага явные вход и выход
- Пользователь понимает, что делает Agent

### 3. Тщательно проектируйте интерфейсы инструментов (ACI)

<AdInArticle />

> «Проектированию человеко-машинных интерфейсов (HCI) уделяют столько усилий — столько же вкладывайте в проектирование интерфейсов "агент-компьютер" (ACI)».

**Практика**:
- Описания инструментов — как отличные docstring для джуна
- Включайте примеры использования и граничные случаи
- Избегайте форматов с точным подсчётом и сложным экранированием

## Workflow vs Agent: как выбирать

| Тип | Особенности | Сценарии | Реализация в OpenCode |
|------|------|---------|--------------|
| **Workflow** | Предопределённые пути кода, фиксированные шаги | Предсказуемые задачи с ясной структурой | Skill, Command |
| **Agent** | LLM сама решает и исследует | Открытые вопросы с непредсказуемыми шагами | Agent + Task tool |

### Блок-схема выбора

```
Пришла задача
    ↓
Шаги фиксированы?
    ├─ Да → Workflow (Skill/Command)
    └─ Нет → Сколько нужно самостоятельности?
              ├─ Мало → Ограниченный Agent (steps + контроль прав)
              └─ Много → Полностью автономный Agent
```

## Пять Workflow-паттернов

### Паттерн 1: Prompt Chaining (цепочка промптов)

**Принцип**: разбить задачу на последовательно выполняемые шаги — вывод каждого шага входит в следующий.

**Сценарии**:
- Задача чётко бьётся на фиксированные подзадачи
- Точностью жертвуем ради... нет, точность покупаем задержкой

**Пример**: перевод + редактура + форматирование

```markdown
---
description: Многошаговая обработка перевода
mode: subagent
steps: 10
---

# Процесс задачи

Выполняйте по шагам, каждый следующий — после прошлого:

## Шаг 1: дословный перевод
Переведите оригинал по предложениям, сохраняя смысл.

## Шаг 2: литературная правка
На основе дословного доведите до гладкого русского изложения.

## Шаг 3: проверка профтерминов
Проверьте точность профтерминов, при необходимости оставьте английский.

## Шаг 4: форматирование
Приведите вывод к целевому формату (Markdown).

# Требования к выводу
Каждый шаг выводит промежуточный результат, в конце — финальная версия.
```

### Паттерн 2: Routing (маршрутизация)

**Принцип**: по признакам входа направить задачу в нужный профильный процесс.

**Сценарии**:
- Разным классам — разная обработка
- Классификация выполняется точно

**Пример**: классификатор проблем кода

```markdown
---
description: Маршрутизатор проблем кода
mode: subagent
---

# Роль
Вы — эксперт по классификации проблем кода: направляете проблемы в верный процесс обработки.

# Правила классификации

Разберите проблему пользователя в коде и определите её класс:

1. **Исправление багов** → вызвать @bug-fixer
   - Признаки: код падает, поведение не то

2. **Оптимизация производительности** → вызвать @performance-optimizer
   - Признаки: работает медленно, много памяти

3. **Аудит безопасности** → вызвать @security-auditor
   - Признаки: затронуты аутентификация, обработка данных, внешние входные данные

4. **Рефакторинг кода** → вызвать @refactor-expert
   - Признаки: код работает, но структуру улучшить

5. **Разработка функций** → не маршрутизировать, обработать напрямую
   - Признаки: реализация новых требований

# Формат вывода
Сначала объясните причину классификации, затем вызовите нужного subagent.
```

**С управлением правами Task**:

```jsonc
{
  "agent": {
    "router": {
      "description": "Маршрутизатор проблем кода",
      "mode": "primary",
      "permission": {
        "task": {
          "*": "deny",
          "bug-fixer": "allow",
          "performance-optimizer": "allow",
          "security-auditor": "allow",
          "refactor-expert": "allow"
        }
      }
    }
  }
}
```

### Паттерн 3: Parallelization (параллелизация)

**Принцип**: несколько задач выполняются одновременно, в конце результаты сводятся.

**Два варианта**:
- **Sectioning (нарезка)**: независимые подзадачи параллельно
- **Voting (голосование)**: одна задача с нескольких точек зрения для точности

**Сценарии**:
- Подзадачи независимы
- Нужны несколько точек зрения для точности
- Время критично, нужно ускорение

**Пример: параллельная проверка качества кода**

```markdown
---
description: Параллельная проверка качества кода
mode: subagent
---

# Задача
Проверить заданный код сразу по нескольким направлениям.

# Параллельные задачи

**Одновременно** вызовите subagent (несколько вызовов Task tool):

1. @security-auditor — проверка уязвимостей
2. @performance-reviewer — разбор производительности
3. @style-checker — проверка стиля кода
4. @test-coverage-analyzer — разбор покрытия тестами

# Правила сведения

Собрав все результаты, создайте сводный отчёт:

## Сводная оценка
- Безопасность: X/10
- Производительность: X/10
- Стиль кода: X/10
- Покрытие тестами: X/10
- **Итого**: X/40

## Сводка проблем
Отсортируйте все найденные проблемы по серьёзности.

## Приоритетные рекомендации
Три проблемы, чинить которые важнее всего.
```

### Паттерн 4: Orchestrator-Workers (оркестратор-исполнители)

**Принцип**: центральный LLM (оркестратор) динамически разбирает задачу, бьёт на части и раздаёт профильным Worker Agent.

**Сценарии**:
- Заранее неясно, какие подзадачи понадобятся
- Сложность задачи неопределённа
- Нужна гибкая реакция

**Пример: оркестратор анализа проекта**

```markdown
---
description: Оркестратор анализа проекта, динамически раздаёт задачи анализа
mode: primary
---

# Роль
Вы — оркестратор анализа проекта: понимаете потребности пользователя и координируете команду экспертов.

# Доступные эксперты

Вызывайте следующих экспертов по мере нужды:

- @architecture-analyst — разбор архитектуры, подходит для «как устроен этот проект»
- @dependency-auditor — аудит зависимостей, подходит для «нет ли устаревших и опасных зависимостей»
- @security-auditor — аудит безопасности, подходит для «есть ли угрозы безопасности»
- @performance-profiler — разбор производительности, подходит для «где возможные узкие места»
- @docs-reviewer — ревью документации, подходит для «полна ли документация»
- @test-analyzer — разбор тестов, подходит для «достаточно ли покрытие тестами»

# Процесс работы

1. **Понять потребность**: разберите, что хочет знать пользователь
2. **Составить план**: решите, каких экспертов вызывать и в каком порядке
3. **Выполнить разбор**: вызовите выбранных экспертов
4. **Свести результаты**: объедините находки всех экспертов
5. **Дать рекомендации**: рекомендации к действию по цельному разбору

# Принципы
- Не переанализируйте: выбирайте экспертов под потребность пользователя
- Простому вопросу эксперты могут не понадобиться вовсе
- Находки экспертов могут породить потребность в новом разборе
```

### Паттерн 5: Evaluator-Optimizer (оценщик-оптимизатор)

**Принцип**: один Agent создаёт контент, другой оценивает — цикл до соответствия стандартам.

**Сценарии**:
- Есть явные критерии оценки
- Итеративные улучшения ценны
- Похоже на человеческий процесс «написание-правка»

**Пример: цикл оптимизации кода**

```markdown
---
description: Итеративный оптимизатор кода
mode: subagent
steps: 15
---

# Роль
Вы — эксперт по оптимизации кода: итеративно улучшаете качество кода.

# Цикл оптимизации

Выполняйте цикл, пока не выполнены цели или не исчерпан лимит шагов:

## 1. Этап анализа
- Прочитайте текущий код
- Найдите точки оптимизации
- Оцените текущий балл качества (см. шкалу оценок)

## 2. Этап оптимизации
- Выберите самую влиятельную точку
- Внедрите оптимизацию
- Не сломайте функциональность

## 3. Этап проверки
- Прогоните тесты — функциональность цела
- Переоцените балл качества

## 4. Этап решения
- Балл качества >= 8 — остановить оптимизацию
- Прирост балла < 0.5 — остановить (маржинальная польза мала)
- Иначе — следующий круг

# Шкала оценки качества

| Балл | Читаемость | Производительность | Безопасность | Покрытие тестами |
|------|--------|------|--------|---------|
| 9-10 | Имена ясные, комментарии полные | O(n) и лучше | Без уязвимостей | >90% |
| 7-8 | Имена разумные, главные комментарии | O(n log n) | Низкие риски | 70-90% |
| 5-6 | В основном читаемо | O(n²) | Средние риски | 50-70% |
| <5 | Понять тяжело | O(n³)+ | Высокие риски | <50% |

Итоговый балл = читаемость×0.3 + производительность×0.3 + безопасность×0.25 + покрытие тестами×0.15

# Вывод
Каждый круг выводит:
- Что оптимизировано в этом круге
- Детализацию баллов по направлениям
- Изменение балла качества
- Решение о продолжении с причинами

Финальный вывод:
- Итоги оптимизации
- Сравнение до и после
- Дальнейшие рекомендации по оптимизации (при наличии)

# Обработка сбоев
- Упавшие тесты: немедленно откатить правки круга, записать причину сбоя, попробовать другое направление оптимизации
- Шаги исчерпаны: вывести текущую лучшую версию и оставшиеся рекомендации
- Дальше не оптимизируется: объяснить причину и назвать достигнутый уровень качества
```

## Три главных компонента дизайна Agent

По исследованию Lilian Weng полноценная агентная система состоит из трёх компонентов:

### 1. Planning (планирование)

**Техники декомпозиции задач**:

| Техника | Описание | Сценарии |
|------|------|---------|
| **Chain of Thought** | «Думай по шагам» | Универсальные рассуждения |
| **Tree of Thoughts** | Разведка нескольких путей рассуждений | Сложные решения |
| **ReAct** | Цикл «мысль-действие-наблюдение» | Нужно взаимодействие со средой |

**Применение в промпте Agent**:

```markdown
# Манера работы

Работаем в режиме ReAct:

1. **Мысль**: разбери текущее состояние, реши следующий шаг
2. **Действие**: выполни конкретное действие (вызови инструмент)
3. **Наблюдение**: разбери результат действия
4. **Повтор**: пока задача не выполнена
```

### 2. Memory (память)

| Тип | Аналог | Особенности |
|------|------|------|
| **Краткосрочная память** | Окно контекста | Ограничена, порядка десятков тысяч токенов |
| **Долгосрочная память** | Внешняя векторная база | Безлимитна, нужен поиск |

**Реализация в OpenCode**:
- Краткосрочная: контекст сессии
- Долгосрочная: интеграция векторных баз через MCP

### 3. Tool Use (использование инструментов)

**Принципы проектирования инструментов**:

1. **Описания ясные**: как docstring для джуна-разработчика
2. **Вход простой**: без сложных требований к формату
3. **Вывод разбираемый**: структурированный, для дальнейшей обработки
4. **Ошибки дружелюбные**: понятные тексты ошибок

## Боевой кейс 1: многоязычная система генерации документации

::: warning Напоминание про руки
Имена `@doc-parser`, `@translator-zh` и подобные в кейсе — это **примеры имён**, встроенных таких Agent в OpenCode нет. Создайте их сами способом из [5.2a Быстрый старт с Agent](./02a-agent-quickstart).

Хорошая новость: Agent кейса 1 довольно простые, поле `description` само по себе — рабочий промпт, с низкой temperature работает. Отдельные `.md`-файлы писать не нужно.
:::

**Задача**: автоматически переводить API-документацию в многоязычные версии.

### Дизайн системы

```
Входной API-документ пользователя
        ↓
    @doc-parser (разбор структуры документа)
        ↓
    @translator-zh (перевод на китайский)
    @translator-ja (перевод на японский)  ← параллельно
    @translator-ko (перевод на корейский)
        ↓
    @doc-formatter (форматирование вывода)
        ↓
    Многоязычная документация
```

### Файл конфигурации

```jsonc
// opencode.json
{
  "$schema": "https://opencode.ai/config.json",
  "agent": {
    "doc-generator": {
      "description": "Оркестратор многоязычной генерации документации",
      "mode": "primary",
      "prompt": "{file:./prompts/doc-generator.md}",
      "permission": {
        "task": {
          "*": "deny",
          "doc-parser": "allow",
          "translator-*": "allow",
          "doc-formatter": "allow"
        }
      }
    },
    "doc-parser": {
      "description": "Разбор структуры API-документации, извлечение переводимого содержимого",
      "mode": "subagent",
      "temperature": 0.1
    },
    "translator-zh": {
      "description": "Эксперт англо-китайского перевода, точно держит технические термины",
      "mode": "subagent",
      "temperature": 0.3
    },
    "translator-ja": {
      "description": "Эксперт англо-японского перевода",
      "mode": "subagent",
      "temperature": 0.3
    },
    "translator-ko": {
      "description": "Эксперт англо-корейского перевода",
      "mode": "subagent",
      "temperature": 0.3
    },
    "doc-formatter": {
      "description": "Форматировщик документации, единообразие многоязычных версий",
      "mode": "subagent",
      "temperature": 0.1
    }
  }
}
```

### Промпт оркестратора

```markdown
<!-- prompts/doc-generator.md -->
---
description: Оркестратор многоязычной генерации документации
mode: primary
---

# Роль
Вы — оркестратор системы многоязычной генерации документации.

# Процесс работы

## 1. Этап разбора
Вызовите @doc-parser для разбора входного документа:
- Извлеките заголовки, описания, параметры, возвращаемые значения и структуру
- Отметьте, что перевести
- Что оставить как есть (вроде примеров кода)

## 2. Этап перевода
**Параллельно** вызовите экспертов-переводчиков:
- @translator-zh: перевод на китайский
- @translator-ja: перевод на японский
- @translator-ko: перевод на корейский

Скажите каждому эксперту-переводчику:
- Структуру документа
- Содержимое для перевода
- Глоссарий (при наличии)

## 3. Этап форматирования
Вызовите @doc-formatter:
- Сведите языковые версии
- Проверьте единообразие формата
- Создайте финальный вывод

# Формат вывода
Создайте предложение структуры каталогов со всеми языковыми версиями.
```

## Боевой кейс 2: конвейер аудита кода

::: warning Напоминание про руки
Имена `@security-auditor`, `@test-auditor` и подобные в кейсе — это **примеры имён**, встроенных таких Agent в OpenCode нет. Создайте их сами способом из [5.2a Быстрый старт с Agent](./02a-agent-quickstart).

В отличие от кейса 1, аудитным Agent нужны профессиональные промпты, чтобы разбор был ценным. Полные примеры создания — ниже.
:::

**Задача**: всесторонний аудит кода PR.

### Дизайн системы

Смешанный паттерн **Parallelization + Orchestrator-Workers**.

```
Изменения кода PR
        ↓
    @audit-coordinator (координатор)
        ↓
    ┌──────────────────────────────────┐
    │  Параллельное выполнение         │
    │  (нарезка Sectioning)            │
    │  @security-auditor              │
    │  @performance-auditor           │
    │  @quality-auditor               │
    │  @test-auditor                  │
    └──────────────────────────────────┘
        ↓
    Сводка всех находок
        ↓
    @report-generator (создание отчёта)
        ↓
    Отчёт аудита
```

### Файл конфигурации

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "agent": {
    "audit-coordinator": {
      "description": "Координатор аудита кода, оркестрирует многоплановый аудит",
      "mode": "subagent",
```

### Промпт координатора

```markdown
<!-- prompts/audit-coordinator.md -->
# Координатор аудита кода

## Обязанности
Координировать нескольких профильных аудит-Agent для всестороннего аудита изменений кода.

## Процесс аудита

### 1. Разбор изменений
Сначала разберите это изменение:
- Какие файлы затронуты
- Тип изменения (новая функция, фикс бага, рефакторинг)
- Масштаб изменения

### 2. Распределение задач аудита
**Параллельно** вызовите аудит-экспертов:

| Эксперт | Фокус |
|------|--------|
| @security-auditor | SQL-инъекции, XSS, обход аутентификации, чувствительные данные |
| @performance-auditor | Сложность O(n²), утечки памяти, N+1-запросы |
| @quality-auditor | Именования, длина функций, дубли кода, SOLID |
| @test-auditor | Покрытие тестами, граничные случаи, качество Mock |

### 3. Сводка результатов
Соберите результаты аудита:

**Определение серьёзности**:
| Уровень | Определение | Пример |
|------|------|------|
| Critical | Удалённо эксплуатируемо, риск утечки данных | SQL-инъекции, захардкоженные ключи |
| High | Требует входа, дефекты функций | Обход аутентификации, утечки ресурсов |
| Medium | Срабатывает при особых условиях | Необработанные граничные случаи |
| Low | Стиль кода, лёгкая производительность | Непонятные имена |

**Разрешение конфликтов**:
- Одна строка кода найдена несколькими аудитами → оставить наивысшую серьёзность
- Противоречивые рекомендации → пометить «нужна ручная проверка»
- Распознавание ложных срабатываний → при согласии 2+ аудиторов, что проблемы нет, — понизить

### 4. Генерация отчёта
Вызовите @report-generator для финального отчёта:
- Резюме для руководства
- Детальные находки
- Рекомендации по исправлению
- Оценка рисков

## Обработка сбоев
- Тайм-аут некого аудит-Agent: запишите и продолжите, в отчёте пометьте «часть аудита не завершена»
- Ошибка некого аудит-Agent: повторите раз, при повторном сбое пропустите и запишите
- Нечего аудировать: сразу верните «аудит не требуется»

## Вывод
Финальный вывод — структурированный отчёт аудита.
```

### Создание экспертных Agent

В конфиге выше заданы параметры и права Agent, но `performance-auditor`, `quality-auditor`, `test-auditor` и `report-generator` без внешних файлов промптов — они работают на промптах моделей по умолчанию. Для задач аудита этого мало: каждому эксперту создайте `.md`-файл.

#### Структура файлов

```
.opencode/
├── agent/
│   └── security-auditor.md    ← можно и сюда
└── prompts/
    ├── audit-coordinator.md   ← координатор (выше уже есть)
    ├── security-auditor.md    ← эксперт аудита безопасности
    ├── performance-auditor.md ← эксперт аудита производительности
    ├── quality-auditor.md     ← эксперт качества кода
    ├── test-auditor.md        ← эксперт аудита тестов
    └── report-generator.md    ← генератор отчётов
```

#### Полный пример: security-auditor.md

Создайте файл `.opencode/agent/security-auditor.md`:

```markdown
---
description: |
  Эксперт аудита уязвимостей безопасности. Фокус OWASP Top 10, инъекционные атаки, обход аутентификации, утечки чувствительных данных.
  Сценарии: ревью PR, сканирование безопасности кода, проверки перед релизом.
  Неприменимо: оптимизация производительности, стиль кода, разработка функций.
mode: subagent
temperature: 0.1
permission:
  edit: deny
---

# Роль

Вы — senior-эксперт аудита безопасности, фокус на поиске уязвимостей в коде.

# Область аудита

Проверяйте по приоритетам:

## Critical (обязательно проверить)
- **SQL-инъекции**: конкатенируется ли ввод пользователя в SQL-запросы
- **XSS**: рендерится ли ввод пользователя без экранирования
- **Захардкоженные ключи**: API-ключи, пароли и токены в коде
- **Обход аутентификации**: доступ к интерфейсам без проверки
- **Обход путей**: файловые операции по пользовательским путям

## High (тщательно проверить)
- **Небезопасная десериализация**
- **SSRF**: URL-запросы, управляемые пользователем
- **Утечки чувствительных данных**: внутренняя информация в логах и ошибках
- **Уязвимые зависимости**: сторонние пакеты с известными дырами

## Medium (обычная проверка)
- **Конфигурация CORS**
- **Защита CSRF**
- **Ограничение частоты**
- **Неполная валидация ввода**

# Формат вывода

По каждой найденной проблеме выводите в формате:

**[Серьёзность] Заголовок проблемы**
- Файл: `path/to/file.ts:Lномер-строки`
- Фрагмент кода:
  \`\`\`
  проблемный код
  \`\`\`
- Описание риска: атакующий может...
- Рекомендация по исправлению:
  \`\`\`
  исправленный код
  \`\`\`

# Ограничения
- ✅ Каждая проблема — с конкретным файлом и строкой
- ✅ Обязательна рекомендация по исправлению, а не только констатация
- ❌ Не сообщайте о теоретических рисках — только о реально существующем в коде
- ❌ Не предлагайте тянуть новые зависимости ради безопасности
```

```markdown
4. **Дизайн модулей**: связность, зацепление, разделение обязанностей

# Формат вывода
```

## Частые ловушки проектирования

| Ловушка | Проявление | Решение |
|------|------|------|
| **Чрезмерный дизайн** | Несколько Agent решают простую задачу | Сначала попробуйте одним Agent |
| **Туманное описание** | Слишком общее description ведёт к неверным вызовам | Конкретизируйте сценарии применения |
| **Бесконечный цикл** | Agent вызывают друг друга без остановки | Задайте лимит steps |
| **Слишком свободные права** | subagent умеет всё | Явно настройте права task, edit и bash |
| **Нет прозрачности** | Непонятно, что делает Agent | Требуйте вывод промежуточных шагов |
