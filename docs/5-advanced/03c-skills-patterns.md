> Урок углубляется в продвинутое применение Skill: совместная работа с MCP, пять процессных паттернов и стратегии распространения — строим пакеты экспертизы корпоративного уровня.

## Главная идея

### Skill + MCP: кухня и книга рецептов

Отношения MCP и Skill представьте как профессиональную кухню:

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Профессиональная кухня (MCP)                      │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐            │
│  │ Плита    │  │Холодильник│  │ Ножи     │  │ Полка со │            │
│  │(инструм.)│  │ (данные)  │  │(действия)│  │специями  │            │
│  └──────────┘  └──────────┘  └──────────┘  │(ресурсы) │            │
│                                            └──────────┘            │
└─────────────────────────────────────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────────┐
│                    Книга рецептов (Skill)                           │
│                                                                     │
│  «Курица гунбао»                                                    │
│  1. Достать из холодильника 200 г курицы                            │
│  2. Нарезать ножом кубиками                                         │
│  3. Плита на сильный огонь, налить масло...                         │
│  4. Добавить специи: сычуаньский перец, сушёный чили...             │
└─────────────────────────────────────────────────────────────────────┘
```

**MCP даёт**:
- Подключения к сервисам (Notion, Linear, GitHub...)
- Доступ к данным реального времени
- Возможность вызывать инструменты

**Skill даёт**:
- Лучшие практики использования этих инструментов
- Оркестрацию многошаговых процессов
- Экспертизу предметной области

**MCP без Skill** — как «кухня без книги рецептов»: пользователь знает, какие инструменты есть, но не знает, как их комбинировать.

### Три класса use-case

По опыту практики у Skill три главных класса:

| Класс | Особенности | Фокус Skill |
|------|------|-----------|
| **1. Создание документов и активов** | Приоритет качеству вывода | Встроенные гайды по стилю, шаблоны, чек-листы качества |
| **2. Автоматизация процессов** | Консистентность многих шагов | Определения шагов, контрольные точки, обработка ошибок |
| **3. Усиление MCP** | Оптимизация использования инструментов | Координация вызовов MCP, встроенные знания области |

## Пять процессных паттернов

### Паттерн 1: последовательная оркестрация процесса

**Сценарий**: многошаговый процесс со строгим порядком

**Пример структуры**:

```markdown
---
name: customer-onboarding
description: Сквозной процесс онбординга клиентов. Обрабатывает создание аккаунта, настройку платежей, управление подпиской.
  Использовать, когда пользователь говорит «онбординг нового клиента», «настройка подписки», «создание аккаунта».
---

# Процесс онбординга клиентов

## Шаг 1: создание аккаунта
Вызов MCP-инструмента: `create_customer`
Параметры: name, email, company

## Шаг 2: настройка платежей
Вызов MCP-инструмента: `setup_payment_method`
Ожидание: подтверждение способа оплаты

## Шаг 3: создание подписки
Вызов MCP-инструмента: `create_subscription`
Параметры: plan_id, customer_id (из шага 1)

## Шаг 4: приветственное письмо
Вызов MCP-инструмента: `send_email`
Шаблон: welcome_email_template

## Откат при сбоях
Если любой шаг упал:
1. Записать причину сбоя
2. Откатить созданные ресурсы
3. Уведомить администратора
```

**Главные приёмы**:
- Явный порядок шагов
- Зависимости между шагами (шагу 3 нужен вывод шага 1)
- Инструкции отката при сбоях

---

### Паттерн 2: координация нескольких MCP

**Сценарий**: процесс охватывает несколько сервисов

**Пример структуры**: передача от дизайна в разработку

```markdown
---
name: design-to-dev
description: Генерация задач разработки из дизайн-файлов. Использовать при упоминаниях «передача дизайна», «Figma в задачи».
---

# Передача от дизайна в разработку

## Этап 1: выгрузка дизайна (Figma MCP)

1. Выгрузить ресурсы дизайна из Figma
2. Создать документ спецификаций дизайна
3. Составить опись ресурсов

## Этап 2: хранение ресурсов (Drive MCP)

1. Создать папку проекта в Drive
2. Загрузить все ресурсы
3. Создать ссылки для доступа

## Этап 3: создание задач (Linear MCP)

1. Создать задачи разработки
2. Приложить ссылки на ресурсы к задачам
3. Назначить инженерной команде

## Этап 4: уведомления (Slack MCP)

1. Опубликовать сводку передачи в #engineering
2. Включить ссылки на ресурсы и задачи
```

**Главные приёмы**:
- Чёткое деление на этапы
- Определение передачи данных между этапами
- Проверка перед переходом к следующему этапу

---

### Паттерн 3: итеративная оптимизация

**Сценарий**: качество вывода требует нескольких улучшений

**Пример структуры**: генерация отчётов

```markdown
---
name: report-generator
description: Генерация качественных отчётов с автоитерацией до достижения нормы.
---

# Итеративная генерация отчётов

## Черновик

1. Забрать данные через MCP
2. Создать первую версию отчёта
3. Сохранить во временный файл

## Проверка качества

Запустить скрипт проверки: `scripts/check_report.py`
Что проверяется:
- Пропущенные разделы
- Несогласованность формата
- Ошибки валидации данных

## Цикл оптимизации

```
WHILE качество не в норме:
    1. Исправить найденные проблемы
    2. Перегенерировать затронутые разделы
    3. Проверить снова
```

## Финальная версия

1. Применить финальное форматирование
2. Создать резюме
3. Сохранить финальную версию
```

**Главные приёмы**:
- Явные стандарты качества
- Цикл итеративных улучшений
- Понимание, когда остановить итерации

---

### Паттерн 4: контекстно-зависимый выбор инструментов

**Сценарий**: одна цель — разные инструменты по контексту

**Пример структуры**: умное хранение файлов

```markdown
---
name: smart-storage
description: Автовыбор лучшего места хранения по типу и назначению файлов.
---

# Умное хранение файлов

## Дерево решений

1. Проверить тип и размер файла
2. Определить лучшее место хранения:
   - Большие файлы (>10MB) → облачное хранилище MCP
   - Документы для совместной работы → Notion/Docs MCP
   - Файлы кода → GitHub MCP
   - Временные файлы → локальное хранение

## Выполнение хранения

По решению:
- Вызвать подходящий MCP-инструмент
- Применить метаданные сервиса
- Создать ссылку доступа

## Обратная связь пользователю

Объяснить, почему выбрано именно это место хранения
```

**Главные приёмы**:
- Ясные критерии решений
- Запасные варианты
- Прозрачность для пользователя (объяснение выбора)

---

### Паттерн 5: доменный интеллект

**Сценарий**: Skill даёт экспертизу сверх доступа к инструментам

**Пример структуры**: финансовый комплаенс

```markdown
---
name: payment-compliance
description: Обработка платежей с комплаенс-проверками. Использовать при трансграничных платежах и крупных сделках.
---

# Комплаентная обработка платежей

## До обработки (комплаенс-проверки)

1. Забрать детали транзакции через MCP
2. Применить комплаенс-правила:
   - Проверить санкционные списки
   - Подтвердить разрешённость юрисдикции
   - Оценить уровень риска
3. Записать комплаенс-решение

## Обработка

IF комплаенс пройден:
    - Вызвать MCP-инструмент обработки платежа
    - Применить подходящие антифрод-проверки
    - Обработать транзакцию
ELSE:
    - Отметить для ручной проверки
    - Создать комплаенс-кейс

## Аудит-трейл

- Записать все комплаенс-проверки
- Записать решения по обработке
- Создать аудиторский отчёт
```

**Главные приёмы**:
- Встроить знания области до действий
- Комплаенс важнее операций
- Полное документирование

## Распространение и обмен

OpenCode поддерживает несколько способов распространения Skill — от локальных до удалённых.

### Пути поиска Skill в OpenCode

OpenCode ищет Skill в порядке:

```
┌─────────────────────────────────────────────────────────────────────┐
│ Приоритет поиска (позже загруженное перекрывает ранее загруженное)  │
├─────────────────────────────────────────────────────────────────────┤
│ 1. Глобальные внешние каталоги                                      │
│    ~/.claude/skills/**/SKILL.md                                     │
│    ~/.agents/skills/**/SKILL.md                                     │
├─────────────────────────────────────────────────────────────────────┤
│ 2. Внешние каталоги проекта (обход от текущего каталога до корня git)│
│    .claude/skills/**/SKILL.md                                       │
│    .agents/skills/**/SKILL.md                                       │
├─────────────────────────────────────────────────────────────────────┤
│ 3. Каталоги конфигурации OpenCode                                   │
│    ~/.config/opencode/skill/**/SKILL.md                             │
│    .opencode/skill/**/SKILL.md                                      │
├─────────────────────────────────────────────────────────────────────┤
│ 4. Дополнительные пути из конфига (skills.paths)                    │
├─────────────────────────────────────────────────────────────────────┤
│ 5. Скачивание по удалённым URL (skills.urls)                        │
│    Кэш в ~/.cache/opencode/skills/                                  │
└─────────────────────────────────────────────────────────────────────┘
```

### Способ 1: положить в локальный каталог

Проще всего — положить в стандартный каталог:

| Каталог | Область | Пояснение |
|------|---------|------|
| `.opencode/skill/<name>/SKILL.md` | Текущий проект | Только для проекта |
| `~/.config/opencode/skill/<name>/SKILL.md` | Глобально | Доступен всем проектам |

### Способ 2: настроить дополнительные пути

В `opencode.json` укажите дополнительные каталоги Skill:

```jsonc
{
  "skills": {
    "paths": [
      "~/my-skills",                    // Абсолютный путь (~ раскрывается в домашний каталог)
      "../shared-skills",               // Относительно каталога проекта
      "/opt/company-skills"             // Абсолютный путь
    ]
  }
}
```

**Сценарии**:
- Общие Skill команды (на NAS или в общем каталоге)
- Один набор Skill для нескольких проектов

### Способ 3: обнаружение по удалённым URL (рекомендуется командам и сообществам)

OpenCode умеет автоматически скачивать Skill с удалённых серверов:

**Как настроить**:

```jsonc
{
  "skills": {
    "urls": [
      "https://your-company.com/.well-known/skills/",
      "https://skills.example.com/index.json"
    ]
  }
}
```

**Формат index.json на стороне сервера**:

```json
{
  "skills": [
    {
      "name": "project-setup",
      "description": "Процесс инициализации проекта",
      "files": [
        "SKILL.md",
        "references/templates.md",
        "references/checklist.md"
      ]
    },
    {
      "name": "code-review",
      "description": "Помощник ревью кода",
      "files": [
        "SKILL.md"
      ]
    }
  ]
}
```

**Структура каталогов на сервере**:

```
https://your-company.com/.well-known/skills/
├── index.json              # Индекс Skill
├── project-setup/
│   ├── SKILL.md
│   └── references/
│       ├── templates.md
│       └── checklist.md
└── code-review/
    └── SKILL.md
```

OpenCode:
1. Забирает `index.json`
2. Скачивает файлы каждого Skill
3. Кэширует в `~/.cache/opencode/skills/`

**Сценарии**:
- Внутренняя библиотека Skill предприятия
- Распространение Skill в опенсорс-сообществе
- Регулярно обновляемые коллекции Skill

### Способ 4: обмен через Git-репозиторий

Связка Git-репозитория и настройки дополнительных путей:

**Шаг 1**: создайте репозиторий Skill

```
my-skills/
├── README.md               # Описание для людей
├── skills/
│   ├── project-setup/
│   │   └── SKILL.md
│   └── code-review/
│       └── SKILL.md
└── examples/
    └── screenshots/
```

**Шаг 2**: участники команды клонируют и настраивают

```bash
# Клонировать в фиксированное место
git clone https://github.com/yourcompany/opencode-skills.git ~/opencode-skills

# Сослаться в opencode.json проекта
```

```jsonc
{
  "skills": {
    "paths": ["~/opencode-skills/skills"]
  }
}
```

**Шаг 3**: обновление Skill

```bash
cd ~/opencode-skills
git pull
```

### Сравнение способов распространения

| Способ | Сценарии | Плюсы | Минусы |
|------|---------|------|------|
| **Локальный каталог** | Личное использование | Просто и прямо | Неудобно делиться |
| **Дополнительные пути** | Общее использование в команде (NAS) | Одна настройка на всех | Нужен общий доступ к файлам |
| **Удалённые URL** | Предприятие и сообщество | Автообновление, версионирование | Нужен свой сервер |
| **Git-репозиторий** | Опенсорс и команды | Контроль версий, удобно colaborar — нет, удобна совместная работа | Нужно вручную делать pull |

## Типичные проблемы

| Симптом | Причина | Решение |
|-----|-----|-----|
| Скачивание удалённого Skill падает | Неверный формат index.json | Проверьте формат JSON и массив files |
| Skill не виден | Неверная настройка путей | Проверьте, правильно ли раскрывается `skills.paths` |
| Конфликт одноимённых Skill | Определены в нескольких местах | Позже загруженный перекрывает, смотрите предупреждения в логах |
| Вызовы MCP падают при загруженном Skill | MCP-сервис не подключён | Проверьте конфигурацию MCP в `opencode.json` |
| Порядок вызовов нескольких MCP путается | Нет явной нумерации шагов | Определяйте порядок «шагами 1/2/3» |
| Бесконечный цикл итеративной оптимизации | Нет условия остановки | Добавьте «максимум N итераций» или порог качества |

   - Координация нескольких MCP: межсервисная оркестрация, деление на этапы
   - Итеративная оптимизация: цикл качества, условия остановки
   - Выбор по контексту: дерево решений, прозрачный выбор
   - Доменный интеллект: комплаенс прежде всего, аудит-трейл
4. **Способам распространения в OpenCode**: локальные каталоги, дополнительные пути, удалённые URL, Git-репозитории
