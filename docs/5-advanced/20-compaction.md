## Когда это пригодится

- Когда нужно: долго дебажить или рефакторить, диалог накопил гору истории
- И не хочется: из-за переполнения контекста вынужденно перезапускать диалог
- Модель ругается: `Error: Request too large for context window`

## Основная идея

### Что такое Context Window?

У каждой LLM-модели есть **контекстное окно (Context Window)** — лимит максимального числа токенов, которые модель «видит» за раз. Превышение лимита — и модель не обрабатывает новые запросы.

**Главные понятия**:
- **Context**: общий размер контекстного окна
- **Input tokens**: текст, отправляемый модели (сообщения пользователя + системный промпт + результаты вызовов инструментов)
- **Output tokens**: ответы, созданные моделью
- **Cache tokens**: токены кэша при использовании Prompt Caching

### Что делает сжатие?

Механизм сжатия OpenCode состоит из двух действий:

1. **Prune (обрезка)**: автоматическая чистка старых выводов инструментов
   - Сохраняет выводы инструментов за последние 40,000 токенов
   - Чистит более старые выводы (содержимое файлов, результаты поисков)
   - Не трогает выводы skill-инструментов (там обычно важное состояние)

2. **Summarize (суммирование)**: генерация сводки через LLM
   - Отправляет историю диалога специальному compaction-агенту
   - Создаёт подробную сводку: что сделано, что делается, планы дальше
   - Заменяет сводкой исходные исторические сообщения — резкое снижение расхода токенов

## Глубокий разбор принципов

### Как считаются проценты Context?

Формула "Context X% used" справа в TUI:

```
Процент Context = (input + output + reasoning + cache.read + cache.write) / model.limit.context * 100
```

**Учитываемые типы токенов**:
- `input`: токены ввода в модель
- `output`: токены вывода модели
- `reasoning`: размышления reasoning-моделей (вроде Claude Thinking)
- `cache.read`: токены, прочитанные из кэша
- `cache.write`: токены, записанные в кэш

### Когда срабатывает автосжатие?

**Главная проверяющая функция** (исходники: `src/session/compaction.ts:32-48`):

```typescript
Условие срабатывания: token_count >= (input_limit - reserved)
где reserved = min(20000, model_max_output)
```

**Разбор формулы**:
1. Считаем потраченные токены: `input + output + cache.read + cache.write`
2. Считаем резерв (reserved): по умолчанию `min(20,000, макс. вывод модели)`
3. Считаем доступное место: `input_limit - reserved`
4. При потраченном >= доступного — срабатывает автосжатие

**Пример расчёта**:
- Модель: Claude Sonnet 4.5 (context = 200,000, input = 200,000, output = 64,000)
- Резерв = min(20,000, 64,000) = **20,000**
- Доступное место = 200,000 − 20,000 = **180,000**
- Сжатие срабатывает при `token_count >= 180,000`

**Зачем буферу reserve token buffer?** (улучшение v1.1.57)
- Гарантирует входному окну место под саму операцию сжатия
- Сама операция сжатия шлёт запрос на сводку — нужен запас места
- Сжатие надёжнее, меньше «сбоев сжатия»

### Подробно о процессе сжатия

<AdInArticle />

#### Шаг 1: обрезка выводов инструментов (Prune)
```typescript
// Сохраняем выводы инструментов за последние 40K токенов
PRUNE_PROTECT = 40_000
PRUNE_MINIMUM = 20_000
```
- Обходим сообщения с конца к началу
- Копим токены выводов инструментов до 40,000
- Выводы сверх лимита помечаются `compacted`
- Реально чистим, только если объём чистки > 20,000 (мелочь не трогаем)

#### Шаг 2: вызов Compaction Agent
- Создаётся скрытый агент (имя: `compaction`)
- Отключаются все права инструментов (`PermissionNext.fromConfig({ "*": "deny" })`)
- Отправляется промпт на суммирование:
  ```
  "Provide a detailed prompt for continuing our conversation above.
  Focus on information that would be helpful for continuing the conversation,
  including what we did, what we're doing, which files we're working on,
  and what we're going to do next considering new session will not have access to our conversation."
  ```

#### Шаг 3: генерация сводки и метка точки сжатия
- Созданная сводка помечается `summary: true`
- В сообщения пользователя вставляется метка `compaction` — записывается точка сжатия
- **Ключевое различие**:
  - Листание истории пользователем: **полная история видна** (база данных не тронута)
  - Отправка модели: **только контекст после точки сжатия** (экономия токенов)

## Контекстные окна популярных моделей

### Источник данных

Свежие данные моделей OpenCode забирает удалённо из **https://models.dev/api.json** (исходники: `src/provider/models.ts`), при каждом старте обновляя локальный кэш.

### Частые модели

| Модель | Провайдер | Context | Output | Порог срабатывания* |
|-----|----------|---------|--------|----------|
| Claude Sonnet 4.5 | Anthropic | 200,000 | 64,000 | ~168,000 |
| Claude Opus 4.5 | Anthropic | 200,000 | 64,000 | ~168,000 |
| Gemini 3 Pro | Google | 1,000,000 | 64,000 | ~968,000 |
| Gemini 3 Flash | Google | 1,048,576 | 65,536 | ~1,016,536 |
| GPT 5.2 Pro | OpenAI | 400,000 | 128,000 | ~368,000 |
| GPT 5.2 | OpenAI | 400,000 | 128,000 | ~368,000 |
| GLM 4.7 | ZhipuAI | 204,800 | 131,072 | ~172,728 |
| DeepSeek Chat | DeepSeek | 128,000 | 8,192 | ~119,808 |

> *Порог срабатывания = context − min(output, 32,000), ориентировочно, точные значения — по models.dev

**Главные выводы**:
- У Gemini 3 Flash самое большое контекстное окно (~1M) — для разбора сверхдлинных документов
- У DeepSeek Chat контекст меньше (128K) — сжатие срабатывает легче
- У серии GPT 5.2 большие лимиты вывода (128K) — запаса резерва хватает

## Повторите за мной

### Шаг 1: посмотрите текущее потребление Context

В правой боковой панели TUI найдите область Context:

```
Context
145,234 tokens 73% used
```

Значит, текущий диалог потратил 145,234 токена — 73% контекстного окна модели.

**Вы должны увидеть**:
- Для GPT 5.2 (context = 400,000) процент будет умеренным
- Для Gemini 3 Flash (context = 1,048,576) процент будет низким

### Шаг 2: сожмите вручную

Когда диалог кажется слишком длинным, сожмите вручную:

**Способ 1: команда TUI**
В поле ввода наберите:
```
/compact
```
или алиас:
```
/summarize
```

**Способ 2: горячие клавиши**
Нажмите `<leader>c` (по умолчанию `,c`)

**Вы должны увидеть**:
- В поле ввода появится подсказка `Compacting...`
- Модель создаст подробную сводку
- После сжатия история диалога заменится содержимым сводки

### Шаг 3: оцените эффект сжатия

После сжатия посмотрите на проценты Context:

```
Context
45,678 tokens 23% used
```

Против 73% до сжатия — расход токенов заметно упал.

**Вы должны увидеть**:
- Старые результаты вызовов инструментов вычищены (вроде содержимого чтений файлов)
- Сохранена подробная сводка диалога
- Дальнейший диалог модель ведёт по сводке

**Важное уточнение** (легко понять неверно):

| Сценарий | Виден ли исходный диалог |
|------|------------------|
| Листание истории пользователем | ✅ Да (база данных не тронута) |
| Отправка модели | ❌ Нет (отправляются только сообщения после точки сжатия) |

Сжатие **не удаляет** исторические сообщения из базы данных — меняется только **контекст, отправляемый модели**. Листать полную историю вверх можно в любой момент.

## Продвинутая настройка

### Где лежит конфиг

OpenCode поддерживает многоуровневую конфигурацию, приоритет сверху вниз:

| Место | Приоритет | Описание |
|-----|-------|------|
| `./opencode.json` | Высокий | Конфиг уровня проекта (рекомендуется для проектных настроек) |
| `~/.config/opencode/opencode.json` | Низкий | Глобальный конфиг (рекомендуется для личных предпочтений) |
| Переменная окружения `OPENCODE_CONFIG` | Наивысший | Путь к своему файлу конфигурации |
| Переменная окружения `OPENCODE_CONFIG_DIR` | - | Свой каталог конфигурации |

### Настройка резерва места (новое в v1.1.57)

При срабатывании сжатия резервируется место под токены, чтобы сама операция сжатия прошла гладко:

**opencode.json**
```json
{
  "compaction": {
    "reserved": 30000
  }
}
```

**Описание параметров**:
- Значение по умолчанию: `min(20000, макс. вывод модели)`
- Назначение: управляет моментом срабатывания сжатия (упреждение)
- Сценарий: при частых сбоях сжатия увеличьте значение

### Отключение автосжатия

Чтобы OpenCode не сжимал автоматически, задайте в конфиге:

**opencode.json**
```json
{
  "compaction": {
    "auto": false
  }
}
```

Или в командной строке:
```bash
OPENCODE_DISABLE_AUTOCOMPACT=true opencode
```

### Отключение обрезки выводов инструментов

Функция Prune автоматически чистит старые выводы инструментов. Чтобы сохранить все выводы:

**opencode.json**
```json
{
  "compaction": {
    "prune": false
  }
}
```

Или в командной строке:
```bash
OPENCODE_DISABLE_PRUNE=true opencode
```

### Свои лимиты контекста моделей

Чтобы поменять лимиты context или output некой модели (например, раньше срабатывать сжатием):

**opencode.json**
```json
{
  "provider": {
    "openai": {
      "models": {
        "gpt-5.2": {
          "limit": {
            "context": 100000,
            "output": 10000
          }
        }
      }
    }
  }
}
```

**Пример сценария**:
- Исходный GPT 5.2: context = 400,000, порог срабатывания ~368,000
- После настройки: context = 100,000, порог срабатывания ~90,000
- Эффект: сжатие срабатывает раньше в диалоге, без переполнения

**Зачем так делать?**
- Отдельные модели деградируют при высоком заполнении контекста
- Хочется сжимать раньше, оставляя больше места генерации
- Экономия затрат на API (меньше входных токенов)

## Типичные проблемы

| Симптом | Причина | Решение |
|-----|-----|-----|
| После сжатия модель не помнит детали | Сводка сжатия потеряла ключевую информацию | Вручную дополните ключевое или перезапустите диалог |
| Сжали, но всё равно переполнение | Слишком длинный вывод модели, съел резерв | Уменьшите max_tokens или возьмите модель с большим контекстом |
| Проценты Context неверные | Данные models.dev устарели, локальный кэш не обновлён | Удалите кэш и перезапустите OpenCode |
| Не хотите сжатие | Отключили автосжатие, но всё равно срабатывает | Проверьте, применяется ли переменная окружения `OPENCODE_DISABLE_AUTOCOMPACT` |

### Низкое качество сводки сжатия

Промпт Compaction Agent фиксированный. Плохое качество сжатия означает:

1. **Проверьте качество исходного диалога**: слишком разрозненные диалоги плохо суммируются
2. **Дополните сводку вручную**: после сжатия введите «дополнение к сводке: ...»
3. **Смените модель**: compaction agent по умолчанию использует модель текущего диалога

### Забывание контекста после сжатия

Сводка после сжатия подробна, но всех деталей не вмещает. Заметили, что модель забыла важное:

1. **Перезапустите диалог**: начните с чистого листа, но потеряете всю историю
2. **Дополните вручную**: после сжатия введите сводку ключевой информации
3. **Настройте качество сводки**: перекройте compaction prompt через плагин (продвинутое использование)
