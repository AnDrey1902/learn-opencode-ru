## Основная идея

В OpenCode встроен мощный набор инструментов отладки `opencode debug`. Они нужны не только для разработки — продвинутым пользователям они помогают диагностировать ошибки конфигурации, проблемы файловой системы и аномалии поведения AI.

## Повторите за мной

### 1. Отладка конфигурации (Config)

Хотите знать, как ваша конфигурация работает на самом деле?

**Важный сценарий**: главная конфигурация OpenCode берётся не только из `opencode.json` — **плагины умеют динамически подмешивать конфигурацию при старте**.

Если хотите убедиться:
- применяется ли конфигурация, подмешанная неким плагином?
- каков **итоговый результат** слияния значений по умолчанию, пользовательской конфигурации и конфигурации плагинов?

Нужна именно эта команда:

```bash
opencode debug config
```

**Пример вывода** (фрагмент):
```json
{
  "$schema": "https://opencode.ai/config.json",
  // Здесь перечислены Agent, объявленные в конфигурации
  "agent": {
    "coder": { ... },
    "writer": { ... },
    "my-custom-agent": { ... } // Проверьте, есть ли свой Agent
  },
  // Здесь может лежать динамически подмешанная конфигурация плагинов
  "plugin_injected_config": { ... }
}
```

::: warning Конфигурации TUI здесь нет
`theme`, `keybinds`, а также настройки прокрутки, курсора и прочие интерфейсные настройки переехали в отдельные `tui.json` / `tui.jsonc`. Команда `opencode debug config` читает главный сервис конфигурации, поэтому отсутствие этих полей в выводе — норма; проверяйте напрямую файлы конфигурации TUI соответствующего уровня и их Schema `https://opencode.ai/tui.json`.
:::

Если в старой главной конфигурации остались `theme`, `keybinds` или `tui`, сначала проверьте, нет ли рядом `tui.json`: при наличии автомиграция пропускается; при наличии только `tui.jsonc` — не пропускается. Без целевого файла после старта TUI должны создаться `tui.json` и `<исходный-главный-конфиг>.tui-migration.bak`; существующий бэкап переиспользуется. Только после успешной записи нового файла и бэкапа старые поля удаляются из главной конфигурации.

> Основание в исходниках: [debug config читает только главный сервис конфигурации](https://github.com/anomalyco/opencode/blob/v1.18.22/packages/opencode/src/cli/cmd/debug/config.ts#L5-L13) и [правила миграции TUI](https://github.com/anomalyco/opencode/blob/v1.18.22/packages/opencode/src/config/tui-migrate.ts#L24-L67).

::: tip 💡 Как посмотреть, какие Agent загружены?
Поле `agent` в `opencode debug config` подтверждает только объявленных в конфигурации Agent и не отражает полный рантайм-список; встроенные Agent дособираются сервисом Agent отдельно. Текущих доступных Agent смотрите в списке Agent в TUI или через Agent API.
:::

### 2. Отладка файловой системы (File и Ripgrep)

OpenCode зависит от ripgrep для сверхбыстрого поиска. Если результаты поиска не те, что ждали, — разбирайтесь этими командами.

**Проверка поведения поиска**:
```bash
# Тестовый поиск
opencode debug rg search "ключевое-слово"

# Дерево файлов (структура каталогов глазами OpenCode)
opencode debug rg tree
```

**Проверка чтения файлов**:
```bash
# Прочитать содержимое файла (в JSON, с метаданными)
opencode debug file read package.json
```

### 3. Отладка Agent и Skill

Когда понаставили кучу плагинов или руками добавили много Skill, бывает состояние **«поставил, а работает ли — непонятно»**.

**Эта команда быстро покажет, какие Skill реально загружены в OpenCode**. Выведет имена Skill и физические пути — главный инструмент разбора конфликтов.

**Список реально загруженных Skill**:
```bash
opencode debug skill
```

**Пример вывода**:
```json
[
  {
    "name": "fanyi",
    "description": "...",
    // Проверяем, файл по какому пути загружен
    "location": "/Users/user/.claude/skills/fanyi/SKILL.md"
  },
  {
    "name": "sync-changelog",
    // Проверяем, не перекрыл ли одноимённый Skill
    "location": "/Users/user/.config/opencode/skill/sync-changelog/SKILL.md"
  }
]
```

**Детали конфигурации Agent**:
```bash
# Полная конфигурация audit-gemini (включая права и промпт)
opencode debug agent audit-gemini
```

**[Продвинутое] Ручное выполнение инструментов Agent**:
Хотите проверить, сможет ли Agent успешно вызвать некий инструмент? Проверьте напрямую:

```bash
# Тест: audit-gemini использует инструмент bash
opencode debug agent audit-gemini --tool bash --params '{"command":"ls -la"}'
```

**Список всех Skill**:
```bash
opencode debug skill
```

### 4. Отладка LSP (языковых серверов)

Если не работают автодополнение кода и переходы к определениям — возможно, проблема в LSP.

```bash
# Диагностика файла (ошибки и предупреждения)
opencode debug lsp diagnostics src/index.ts

# Поиск символов рабочей области
opencode debug lsp symbols "AppController"

# Структура символов одного файла
opencode debug lsp document-symbols src/index.ts
```

### 5. Состояние системы (Paths и Scrap)

**Ключевые пути**:
Не знаете, где лежат данные?
```bash
opencode debug paths
```

**Пример вывода**:
```
data       /Users/username/.local/share/opencode
config     /Users/username/.config/opencode
log        /Users/username/.local/share/opencode/log
cache      /Users/username/.cache/opencode
```

**История проектов (Scrap)**:
OpenCode записывает все открывавшиеся проекты (Worktree).
```bash
opencode debug scrap
```

### 6. Отладка снапшотов (Snapshot)

Сжатие контекста OpenCode опирается на механизм снапшотов.

```bash
# Отслеживать текущее состояние снапшотов
opencode debug snapshot track

# Посмотреть diff снапшотов
opencode debug snapshot diff <hash>
```

## Шпаргалка команд

| Команда | Назначение | Типичный кейс |
|------|------|----------|
| `debug config` | Итоговая главная конфигурация | Проверить, применяются ли модели, Agent, права из главной конфигурации |
| `debug agent <name>` | Детали Agent | Проверить промпт, права, список инструментов |
| `debug agent --tool` | **Ручное выполнение инструмента** | Проверить формат параметров, протестировать права |
| `debug skill` | Список Skill | Убедиться, что Skill загружены, посмотреть пути загрузки |
| `debug rg search` | Тестовый поиск | Разобрать проблему «файлы не находятся» |
| `debug file read` | Чтение файла | Проверить, читается ли содержимое с метаданными |
| `debug file status` | Состояние файлов | Посмотреть интеграцию со статусом Git |
| `debug paths` | Пути | Найти лог-файлы, проверить пути при очистке кэша |
| `debug lsp` | Отладка LSP | Разобрать неработающие автодополнение и переходы |
| `debug scrap` | Список проектов | Найти ID исторических проектов |

## Типичные проблемы

| Симптом | Причина | Решение |
|-----|-----|-----|
| `command not found` | Старая версия OpenCode | Обновитесь до свежей версии |
| Слишком много вывода | Большой объём JSON | Перенаправьте в файл через `> debug.txt` |
| `debug agent` ругается | Не указано имя Agent | Имя обязательно, например `opencode debug agent coder` |

## Итоги урока

Главная ценность команды `opencode debug` — **«видимость рантайма»**:

1.  **Config**: видите **итоговую** конфигурацию после подмешивания плагинов, а не статичный файл.
2.  **Skill**: видите **реально загруженные** список и пути — убеждаетесь, что ничего не проигнорировано и не перекрыто.
3.  **Agent**: видите полный контекст и права, можете даже симулировать выполнение.

Когда кажется, что OpenCode «сломался», — сначала просветите этими командами: обычно оказывается, что дело в конфигурации, а не в настоящем баге.
